Browser side agent deployment runs into three issues that are easy to overlook in early development. API keys placed in client side code are extractable by anyone who opens the browser developer tools, so any keys the browser uses are effectively public. Chorus policies block direct browser calls to many LLM and tool endpoints by default, which means either configuring Chorus on the backend service,
[02:47] or routing through a server-side proxy. Rate limits applied per API key behave differently when many browsers share one key. One user can exhaust the quota for everyone, versus when each browser has its own key, which reintroduces the key exposure problem. Embedding works best for applications where the agent is a thin layer over a back-end that holds the credentials, handles cores, and manages rate limiting on the server-side. For prototypes, internal tools where keys can be reasonably trusted
[03:16] and applications that already proxy LLM calls through their own backend, browser-side agent logic is reasonable. For anything customer-facing with cost or security implications, the agent belongs in a backend service that the browser calls through your own authenticated API. Long-running and multi-agent systems are also poor fits for the embed pattern because they need a strong separation of concerns that browser execution makes hard.
