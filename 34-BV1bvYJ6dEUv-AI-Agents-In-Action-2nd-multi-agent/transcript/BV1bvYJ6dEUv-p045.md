Section 8.3.8 Cost Control and Model Routing Agent costs are real and often surprising at scale, but the right framing is cost relative to value rather than cost in absolute terms. An agent that costs 50 cents per interaction is expensive,
[13:21] if it replaces a $0.10 lookup, and cheap if it replaces a $50 human support call. Cost decisions make sense only in the context of what the agent is replacing or producing, and managing costs without that framing leads to optimizations that erode value. Three patterns drive most cost reduction in production agent systems, each with concrete trade-offs worth understanding. Context trimming reduces the tokens sent on every call by summarizing or removing conversation history,
[13:49] dropping irrelevant tool descriptions, and using structured outputs that constrain response length. The cost savings are real, but tight summarization can break the agent's coherence across multi-turn conversations. Catching at multiple layers, prompt caching for repeated system prompts and tool descriptions, response caching for idempotent tool calls, embedding caching for retrieval queries, typically cuts costs by 30% to 80% on hot paths with minimal effect on quality,
[14:19] which is why most production deployments enable it before any other optimization. The catches that caches need in validation strategies and stale caches can produce stale agent behavior in ways that are hard to diagnose. Routing requests to cheaper models for simpler tasks, as covered in the previous section, is the third lever, but it is the riskiest of the three because an incorrect model selection can degrade output quality across an entire user-facing interaction. As a starting point,
[14:48] instrument cost per session, cost per resolved task, and cost per user before applying any optimization. The teams that succeed at managing agent costs are the ones that measure the cost to value ratio first and then optimize the parts of the system where the ratio is worst rather than reaching for cost reduction patterns generically. Routing by intent means classifying the user's request and dispatching it to the right downstream model or agent.
[15:16] Routing decisions matter disproportionately because a wrong route produces a wrong answer, regardless of how good the downstream agent is. For this reason, most production systems use a frontier model for routing rather than a smaller one, even though small models are cheaper. Routing-specific small language models exist and are improving, but they currently lag frontier models on production quality routing accuracy across diverse inputs. The pattern of small model for routing, large model for reasoning,
[15:45] is real but worth treating as an optimization to apply after measuring routing quality with a Frontier model, not as a default starting point. The cost savings are meaningful when routing volume is high, but only when the smaller model's routing accuracy stays close enough to the Frontier baseline not to erode end-to-end quality. Routing is also a reason to break agents into workflows with multiple discrete steps, where each step can use a different model depending on task complexity.
[16:13] The right framing is that routing is both an architectural decision and a model selection decision, and both need evaluation before committing to a smaller model for the routing layer. Trimming context is another major lever for reducing tokens and cost, and it pays back on every LLM call once the system grows beyond a handful of agents and tools.
