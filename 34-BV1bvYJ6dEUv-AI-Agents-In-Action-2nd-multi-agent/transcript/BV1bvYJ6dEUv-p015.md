Using MCP even internally lets us keep a clean separation of concerns and makes the resulting code extensible and portable across agents. The trade-off is real and worth naming. MCP adds a server process, a client connection, and a protocol layer between the agent and the function it is calling.
[01:55] For tools that already run in the same Python process as the agent, that means extra latency on every call. Typically a few milliseconds for STDIO, more for HTTP, and an extra failure mode. The server can be unreachable when the function would have just worked. It also means an extra layer of code to run, deploy, and debug. The right rule of thumb, reach for MCP when the tool is genuinely external, a different service, a different teams code, a different deployment unit,
[02:24] or a capability you want to share across multiple agents, and prefer in-process function calls when the tool is internal logic that only this agent uses. Internal MCP for everything makes for clean architecture diagrams and noisy production systems.
