## 1. 这一节做什么

这两段是课程的答疑场（Office Hours）。Amal 和 Shreya 不讲课，只回答学员在自己项目里卡住的问题。学员带来的问题都很具体：类别不平衡时要不要分层抽样、评测太贵怎么办、我已经有一套 rubric 了还要不要做开放编码、怎么把 persona 分类、多轮对话的错误怎么重放、Judgey 能不能直接拿来用、给老板看的看板上该放什么指标、零到一没有生产数据怎么评测、RAG 到底是检索坏了还是生成坏了、该不该自建标注工具、工具要不要写进 system prompt、上下文窗口能用多少、长文档怎么切块、错误降不到零怎么办。

所以这一节的「产物」不是一段能跑的 pipeline，而是四样可以照着填的东西：

1. **一张决策表**：遇到某个具体症状时，先问什么问题、再做什么动作（第 4.1 节）。
2. **一份数据模型草案**：把 trace、failure mode、judge 结果、人工标注落成表结构（第 4.3 节，示意）。
3. **一张上下文预算表**：70% / 35% / 50 页这三个数字怎么落到你的模型上（第 4.4 节）。
4. **一份给干系人的口径**：全局错误率怎么算、什么该单列、被问「为什么不是 0」怎么答（第 3 节 Stage 5）。

按第 3 节的顺序走一遍，你会在自己的项目里得到：一份 failure mode 清单、一组校准过的 LLM judge、一张 prevalence（普遍率）报表、一份汇报口径、以及 RAG / 工具调用 / 长文档三个场景的处置方案。

## 2. 讲师原话

先看「不平衡」和「分层抽样」的区别。讲师把它们拆成两件事：不平衡是**指标选错**的问题，分层抽样是**采样覆盖**的问题。

> "分层抽样和类别不平衡有点不同，但两者相关。即使维度不多，也会出现不平衡。不平衡指的是，你的失败率没那么高，比如只占 10%。"
> —— p023 [00:55]

> "大多数时候数据都是不平衡的。这时候你不该用 accuracy 这种指标，因为纯靠运气也能拿到很高的准确率。如果失败率是 10%，你一直猜 pass 就能有 90% 的准确率。"
> —— p023 [01:24]

分层抽样的判据是「这个维度对业务重不重要」，而不是「数据量够不够」：

> "你要做的是一个判断：这些维度在你的业务里是不是都重要？比如不同的地理区域、不同种类的用户，甚至不同的产品。你想确保每一个维度都被度量到，并且被赋予它应有的权重。但这里存在不平衡——不是每个区域、每个维度的数据量都一样，实际上分布非常倾斜。这时候你就要做分层抽样，确保你关心的那些维度有足够的数据，让你能度量它们、围绕它们建立指标。"
> —— p023 [02:21]

关于评测成本，讲师先承认事实：

> "evals 不是免费的。"
> —— p023 [03:20]

然后是成本收益的判据：

> "在错误分析里，我总能找到很多低垂的果实，是那种很琐碎的修复——代码里的 bug，或者对 prompt 非常明显的改动。在我看来它们不值得单独做一个 eval，因为这是一个成本收益的权衡。你要对那种你预期会反复迭代的东西做 eval。有些 eval 非常便宜，比如基于代码的 eval，写起来非常直接，那更像代码里的单元测试，这种你就该写。但当你走到那些更贵的测试、需要反复迭代、需要做对齐的时候，你就得想：我真的会用这个 eval 吗？它是一个能帮我迭代这个问题的工具吗？如果问题怎么修很清楚、修没修好也很清楚，那可能直接修就行了。"
> —— p023 [03:47]

如果只能排一个优先级，讲师给的是：

> "如果把我教的所有东西从最高杠杆排到最低杠杆，错误分析我认为是 ROI 最高的。做 LLM judge、并且投入精力让自己能信任这些 judge，也是极高的 ROI，因为这样你就可以把它部署到所有无标注的 trace 上，并且相信它的结果。所以我会说这是最重要的两件事。至于 prompt 策略和技巧、怎么做强化学习、怎么微调模型等等，我觉得所有这些的优先级都低于真正掌握错误分析和 LLM judge。如果你把这两件事做扎实了，你就能为自己造出一个飞轮。"
> —— p023 [04:38]

有学员已经带着六个维度（创造力、情节、语法、上下文追踪、事实知识、推理）做 Tiny Stories 项目，人工和 judge 的一致率 90% 以上，但觉得「和课上教的不一样」。讲师的回答是：带着假设进场没问题，但别把假设当终点。

> "我很喜欢这个问题。很多时候你其实是有某种形式的评分标准的。你不必完全 blind、完全没有轴心编码地进场。我们的意思是：如果你带着一些东西进场，要意识到自己的偏见，但仍然要做开放编码和轴心编码。不要相信这就是你唯一会有的评分标准，去做开放编码，往这份标准里加东西，造出新的轴心编码。"
> —— p023 [07:01]

> "开放编码不管在什么场景下都是一样的做法。我会在一百个故事上做开放编码，看看能不能发现一些奇怪的东西——那些落不进你六个维度里任何一个的东西。我敢打赌你一定能发现点什么。"
> —— p023 [07:30]

关于 persona 分类，讲师反对先找工具：

> "我不一定会去找现成的工具。我会用 LLM 来给 persona 分类。用这个来帮我做数据分析，帮我抽样做错误分析。如果你发现 persona 分类的效果足够好，你甚至可以把它当成一个 router 来用。我会保持简单。对于 persona 分类，LLM 是相当擅长的，所以我猜它会工作得不错。"
> —— p023 [09:17]

关于多轮对话的错误重放，讲师对「真实」给了一个很宽的定义：

> "我会尽量从真实的 trace 开始。不过「真实」本身也是一个光谱：trace 是由人产生的，但这个人可以是同事，或者我组里的其他人，假装成某个用户——我说的「真实」就是这个意思。我确实喜欢先想清楚 persona 这个做法：一旦我搞清楚了失败模式是什么、persona 会是什么，我就能对一个用来模拟该 persona 的 LLM agent 有信心。但如果这两样都还没有，我从来不会去完全合成地生成一段对话，然后指望从中看出错误模式会是什么。"
> —— p023 [10:45]

有人问 Judgey 能不能直接用在非对话的工作流上，讲师把它的能力边界说得很死：

> "Judgey 只告诉你一个失败模式的普遍率是多少。具体来说，如果你有几千条无标注的对话，它会告诉你这些对话里有多大比例表现出了这个失败模式。它不告诉你怎么改进，也不给你任何开放式的反馈。那种事你得自己用某种方式做——你完全可以先用一个 LLM judge 把你的 trace 标成好和坏，然后让另一个 LLM 只盯着那些坏的标签，提出对 prompt 的可执行改进。这完全没问题。但这条反馈回路你得自己搭回你的产品里。"
> —— p023 [13:54]

关于给干系人看什么，讲师的口径是「合成一个数，但背地里准备好证据」：

> "这取决于干系人的水平和 sophistication。如果他们是数据科学家，看起来会完全不一样。我尽量做到尽可能简化。如果我有一组 LLM judge，我会报一个全局错误率，它是一个复合指标——是不是存在任何一种错误。并不是说我只有一个 judge，我有很多 judge，但就是给个高层的感觉：我们认为有多少比例的对话是好的。如果受众不那么专业，我就不展示置信区间之类的东西，因为信息量太大了，他们不会理解。但我会准备好回答「你们怎么知道这个数是好的」这个问题，并且有一个很好的故事：我们拿它和人工标注做过对比，我们知道它好是因为某某某。这个你可以放在兜里，但通常我不展示。"
> —— p023 [16:17]

如果当下有热点问题，讲师的建议是把热点从全局指标里拎出来单列：

> "你得读一下空气。有些错误就是所有人都在想的热点话题，就是当天的新闻。那你一定要把它做成头号指标之一。如果所有人睡不着觉担心的就是某个问题，那就把它做成那个问题，不要把它藏在全局指标里。这有点像新闻业，你得预判你的受众最看重什么，然后据此调整你的呈现。"
> —— p023 [17:12]

被追问「为什么是 5% 而不是 0%」怎么答：

> "我尽量让人接受一个预期：它在所有地方都不可能是 100%。而且更多时候，你在一个轴上改善了，其他轴有时会跟着变化。所以你总可以把它框成一个取舍：我们可以把所有资源投进去，把某一个失败模式压到零，但我们的资源是有限的，谁知道其他失败模式会怎样——也许它们的失败率会上升，也许会出现我们从来没想过的新失败。把它呈现成「没有什么是完美的，但 95% 仍然能带来价值」，然后问题就变成「我们想把资源分配到哪里的性价比最高」，这样会更有建设性。"
> —— p023 [18:09]

对于零到一、上线前没有生产数据的团队（法律文书抽取，70 多个字段只有部分覆盖）：

> "那种情况下，很难说你在上线前就能做到 100%。把预期设好，然后尽量把生产上的飞轮、数据飞轮转起来：你能看到生产里真实的数据是什么，然后基于它做错误分析，为每一个失败模式建新的 LLM judge。我会试着这么做。另外，你可以根据字段在文档里的位置去预判哪些字段可能出错。做长文档处理的人都知道，文档中间的信息比两端的 information 更难推理。如果你有这类假设，也许可以生成合成数据去验证这些假设。但这也可能过度了：你不想把太多精力花在假设的失败模式上，而资源本可以花在别处、去修真实存在的错误。所以在合成数据这件事上我会比较谨慎。"
> —— p023 [20:30]

RAG 那段是 P24 最有信息量的案例。场景是一家大型云厂商（不是 Amazon 也不是 Google，比它们小一点）的内部客服 Agent，给自家客服坐席用。讲师说：

> "首先的问题是：我们遇到的是生成问题，还是检索问题？很多人是不做错误分析的。我发现几乎没人在做错误分析。你上完这门课，就会成为教所有人做错误分析的那个人，这会是你的超能力。但现实是，人们会迷路，只会说「我拿不到想要的答案」。我看到的常见错误，就是没有认真去看检索出来的到底是什么。在这个客服机器人的案例里，他们的基础设施只允许给 LLM 看七篇文档，是一个非常硬的截断，这也影响了他们该关注什么指标。"
> —— p024 [02:47]

> "他们的场景是：有很多文档里都可能含有正确答案。所以真正需要的是一个叫 hit rate 的指标——这七篇文档里，有没有任何一篇包含答案。当你真正深入一个问题时，你可能得跳出 precision、recall 这些指标。你得看这个问题的动态是什么样，检索的动态是什么样。"
> —— p024 [03:42]

> "我们做的第一件事是错误分析。我们问：问题在哪？然后发现主要问题在检索。于是我们聚焦检索，做了检索上的一堆事，比如做数据分析，发现知识库根本没被索引；发现他们没有好的标注数据集，我们自己标了一些；我们还做了大量的合成数据生成。这些问题全都源于没做错误分析。几乎所有问题都源于没做错误分析。"
> —— p024 [04:39]

关于该不该自建标注工具，讲师的态度是「笨办法就是聪明办法」：

> "我很喜欢笨办法。笨就是聪明，很多时候确实是这样。所以有时候我整套评测就在 notebook 里做：把日志写进本地 SQLite 数据库，拉进 notebook，用几个 notebook 跑报告，就这些。它不酷，但非常有效，而且能跑。"
> —— p024 [06:28]

> "很多时候我会用这些框架——Braintrust、LangSmith、Phoenix——我只把它们当数据库用，就这些。所有应用我都建在它们之上。我用它们的唯一原因、或者说主要原因，是留一个逃生出口：如果有人跟我说「我想要一个能翻这些东西的界面」，我就把这个工具的 UI 给他，说「这儿」，但我所有自定义的东西都建在它上面，读写它。"
> —— p024 [07:27]

关于工具要不要写进 system prompt：

> "我不确定你是否一定要把它们写进 system prompt。我看到的主要问题是：工具被引用的方式不一致。所以也许简化一下，我们干脆不在 system prompt 里包含工具，只确保工具本身的描述非常好。然后如果我们发现 LLM 不擅长调用正确的工具，那时也许需要在 system prompt 里加上「如何调用工具」的模式。我大致会这么处理。但最主要的「不要」是：你不能有互相冲突的信息，也不能在一个地方提到某个工具、在另一个地方又不提。"
> —— p024 [10:17]

上下文窗口怎么用：

> "我通常会把上下文窗口的使用上限控制在 70%。如果这个任务实际上是所谓的变长输出——比如我要从一份文档里抽出所有实例，或者要对上下文里的每一个词都给予注意力——那我的上下文窗口会降到有效窗口的 35%。换句话说，我的有效上下文窗口是标称窗口的 35%。实践上，我不会放超过 50 页 PDF 在一个 prompt 里。我通常用 GPT-4.1 系列，也许现在是 5，我不确定。"
> —— p024 [11:43]

Shreya 补了按「领域单元」而不是按 token 思考 chunk 的做法：

> "我也倾向于用页、以及文档里独立的章节或者单元来思考 chunk。我真的尽量不按 token 去想，因为我根本不知道 200 个 token 意味着什么，我得在脑子里把它换算成字符或者词。我发现按整个单元来推理更容易，就是领域专家实际推理的那些单元：文档的章节和页面。"
> —— p024 [12:13]

反例是 LangChain 里那一堆 splitter：

> "你可能直接 import LangChain，用它那三十来种 chunk splitter：有按 token 大小的，有按段落、换行的，还有各种东西。我最喜欢的是递归分割器——我心想这是什么？为什么需要按逗号递归地分割？这对我来说讲不通。我理解大家都想要「按一个按钮就得到一个 AI 应用」，但它不会那样好好工作，所以最好还是认真想一想。"
> —— p024 [13:35]

关于错误降不到零时在关键路径上拦截：

> "有 guardrails 这个话题，你可能已经接触过了。guardrails 最少见的用法，我觉得主要是在遮蔽个人身份信息这类场景里。任何 eval 都可以放进关键路径跑，问题只是关键路径本身——给用户一个答案。你甚至可以把 LLM judge 本身放进去。唯一的问题是：是不是太贵？是不是太慢？是不是成本太高？很多时候这是产品特定问题。"
> —— p024 [15:56]

> "把错误降到零的成本是无限的。你只能不断逼近零这个极限。"
> —— p024 [16:24]

用户侧的体验怎么处理：

> "用户那边其实是这样：界面上显示「我们还在思考」「我们正在检索更多信息」之类的，用户看到的就是一个转圈。然后它实际上是在自我纠正。这没问题，我见到的就是这样。"
> —— p024 [17:45]

以及一个被低估的做法：

> "另一个我觉得被讨论得不够多的 guardrail 是近似法。你可以写一个基于代码的 guardrail，去近似判断答案是不是在幻觉：真的去检查答案里的每一个词，确认这个词出现在某一个工具的输出里。这是一个近似，但它可能非常有用。所以我会对这个基于代码的 guardrail 本身做 eval，看看它对你来说够不够好，然后你就可以把它放在关键路径上跑。它可能不会把你的失败率降到零，但可能会大幅降低。我非常喜欢这种 95% 近似度的、基于代码的 guardrail，我一直在用。"
> —— p024 [18:41]

最后是长文档（住院病历平均 700 页，可能到 5000 页，要抽多个诊断编码）的 chunk 策略：

> "这个做法在法律场景里也经常出现：我们从每份文档里抽取 metadata，包括摘要、目录、文档类型，以及各种你能抽出来的东西。你可以用 LLM 做这个抽取，我们也这么做。然后我们用这些 metadata 去增强每一个 chunk。这样每当 LLM 在推理某个 chunk 时，它都拥有理解这个 chunk 所需的上下文。"
> —— p024 [21:29]

> "一般来说，在评测流程里我会说：一开始让 metadata 尽量扩张，然后如果你发现性能太低、准确率很差，也许是因为你往上下文窗口里塞了太多脏东西，那时再开始考虑从 metadata 里删。从 metadata 里删东西比往里加容易得多。"
> —— p024 [23:26]

## 3. 从零复现

这一节把上面这些判断整理成一条可以照着走的流水线。每个 Stage 写清楚：**你要做什么、产出什么、判断标准是什么**。这不是新知识，是把讲师在答疑里给出的判据按执行顺序重排。

### Stage 0：先给自己的项目定位（10 分钟）

拿一张纸，回答四个问题：

1. 我的系统输出是**一段对话**、**一份结构化抽取结果**，还是**一次工具调用序列**？
2. 我现在有没有**生产 trace**？有多少条？有没有人工标注？
3. 我的失败率大概是多少？（不知道就写「未知」——这本身就是 Stage 2 要解决的问题）
4. 我对这个领域有没有足够的直觉，能提前列出失败模式？

第 4 题的答案决定了你从哪头进场。讲师的原话是：做文档处理做久了，会先列「我预期会看到哪些错误」；但如果让他去做一个食谱聊天机器人，他会先想 persona，因为他对那个任务的 LLM 失败方式没有很细的直觉。

> "如果我在为一个新领域搭文档处理或文档分析的 pipeline，我可能会先从我熟悉的那些错误开始——也就是我预期会出现的错误，而不是先想 persona。但如果你让我去做一个食谱聊天机器人，我会先从 persona 开始，因为我觉得自己对那个 LLM 任务没有专业知识，也没有关于 LLM 在那个任务上如何失败的很细的直觉。"
> —— p023 [11:36]

**产出**：一句话写下「我的进场点是 failure mode 还是 persona」。

### Stage 1：先把指标口径修对（不平衡 + 分层）

**Step 1.1 算失败率，判断是否不平衡。**

取你手上任意一批 trace，数出失败条数 ÷ 总条数。讲师给的典型值是 10%。

如果失败率远低于 50%，**不要用 accuracy**。理由是可以算出来的：失败率 10% 时，「永远输出 pass」这个零模型的 accuracy 就是 90%。

> "如果失败率是 10%，你一直猜 pass 就能有 90% 的准确率。"
> —— p023 [01:24]

**Step 1.2 列出业务维度，决定要不要分层抽样。**

讲师给的维度例子：地理区域、用户类型、产品线。判据是「这个维度在你的业务里重不重要」，不是「这个维度数据多不多」。

做法：把每个维度的样本占比列出来。如果某个重要维度只占 5%，而你总共只有 100 条样本，那这个维度只有 5 条——算出来的比率没有意义。这时候就要**按维度分层抽样**，保证每个你关心的维度都有足够的样本量去建指标。

![p023 02:15 讲师解释分层抽样要按业务维度取样、保证每个维度可度量](images/p023_0135s.jpg)

**产出**：一张「维度 × 占比 × 现有样本数 × 目标样本数」的表。这张表在第 5 节有算例。

### Stage 2：做错误分析（这是 ROI 最高的一步，先做它）

**Step 2.1 取样本。** 讲师提到的量级是 100 条起：

> "我们做过一个例子，手上只有 100 条标注 trace，那可能就没那么让人崩溃。"
> —— p023 [20:02]

**Step 2.2 开放编码。** 一条一条看，用一句话描述「这条为什么不好」。不要套你已有的分类，先让它自然长出来。

**Step 2.3 轴心编码。** 把 Step 2.2 的描述聚类成 failure mode，每个 failure mode 给一个名字、一句定义、一个正例、一个反例。

**Step 2.4 如果你已经有 rubric，仍然要做 2.2 和 2.3。** 这是讲师对 Tiny Stories 那位学员最直接的回答：带着六个维度进场是可以的，但要在一百个样本上做开放编码，专门找「落不进这六个维度」的东西。

![p023 06:46 讲师回应已有六维评分标准的学生项目：仍要做开放编码扩充 rubric](images/p023_0406s.jpg)

### Stage 3：分诊——哪些错误值得建 eval，哪些直接修

对 Stage 2 产出的每一个 failure mode，问三个问题：

| 问题 | 答「是」→ | 答「否」→ |
|---|---|---|
| 修法是不是一眼就看出来（代码 bug、明显的 prompt 笔误）？ | **直接修**，不建 eval | 进下一问 |
| 修完之后，「有没有修好」是不是一眼就能看出来？ | **直接修**，不建 eval | 进下一问 |
| 我会不会在这个问题上反复迭代很多轮？ | **建 eval** | 先记下来，暂时不建 |

讲师的判据原文是：「如果问题怎么修很清楚、修没修好也很清楚，那可能直接修就行了。」

同时注意成本分层：**基于代码的 eval 便宜，像单元测试，该写就写**；需要人工对齐、需要反复迭代的 judge 才贵，贵的东西才需要论证值不值。

![p023 05:15 讲师按杠杆率排序：错误分析与可信的 LLM judge 优先级最高](images/p023_0315s.jpg)

### Stage 4：建 judge，并且投资于「能信任它」

**Step 4.1** 为每个通过 Stage 3 筛子的 failure mode 写一个 judge prompt（模板见第 4.5 节，示意）。

**Step 4.2** 人工标注一批样本，和 judge 的判定比对，算一致率。那位学员报的数字是 90% 以上，这个量级可以作为参考起点——注意这是学员报的，不是讲师给的门槛，**课里没有给一致率阈值**。

**Step 4.3** 一致率不达标就改 prompt 定义，不要改判据去迁就 judge。

**Step 4.4** 只有在你信任这个 judge 之后，才把它放到无标注 trace 上跑。这就是讲师说的「部署到所有无标注 trace 上，并且相信它的结果」。

### Stage 5：算 prevalence，再做闭环改进

**Step 5.1 算普遍率。** 用 judge 跑全量无标注 trace，得到「有多大比例的对话表现出这个 failure mode」。这就是 Judgey 那一类工具的能力范围。

**Step 5.2 只取 fail 的 trace，喂给第二个 LLM，让它提改进建议。** 讲师的原话是「让另一个 LLM 只盯着那些坏的标签，提出对 prompt 的可执行改进」。

**Step 5.3 人读这些建议，挑能落地的改。** 讲师强调这一步是人来判断：「然后你读一遍，看看哪些讲得通。」

**Step 5.4 改完重跑 Step 5.1**，看 prevalence 有没有降。这就形成了飞轮。

![p023 14:16 讲师给出闭环做法：一个 judge 打标，另一个 LLM 只看失败 trace 提改进](images/p023_0856s.jpg)

### Stage 6：面向干系人的汇报口径

**Step 6.1 合成一个全局错误率。** 讲师的做法是：不是只留一个 judge，而是保留多个 judge，但对外报一个复合指标——「是不是存在任何一种错误」。

**Step 6.2 判断受众水平。** 数据科学家受众：可以放细节。非专业受众：不放置信区间，但要准备好被问「你们怎么知道这个数是好的」，答案必须是「我们和人工标注做过对比」。

**Step 6.3 把当下的热点错误单列。** 不要把它藏在全局错误率里。

**Step 6.4 主动管理「为什么不是 0」的预期。** 用取舍框架回答：资源有限，压一个轴可能抬另一个轴，95% 也有价值，真正的问题是资源往哪投。

![p023 15:46 讲师讲干系人看板：报复合的全局错误率，热点问题单独列出](images/p023_0946s.jpg)

### Stage 7：RAG 场景的额外一步——先分诊

如果你的系统是 RAG，在 Stage 2 之前先回答一个问题：**这是生成问题还是检索问题？**

讲师描述的案例里，团队的直接反应是「答案不好」，但错误分析后发现主因在检索。具体做了三件事：

1. 数据分析了知识库，发现**知识库根本没被索引**；
2. 发现**没有好的标注数据集**，于是自己标了一批；
3. 做了**大量合成数据生成**。

指标上，因为基础设施只允许把 7 篇文档喂给 LLM，所以用 **hit rate**：「这七篇文档里，有没有任何一篇包含答案」。讲师明确说，这种情况可能要跳出 precision / recall。

![p024 04:03 讲师复盘 RAG 案例：用 hit rate 判断七篇文档里有没有答案](images/p024_0243s.jpg)

### Stage 8：工具调用场景——system prompt 与 schema 的一致性

按讲师给的顺序做，不要一上来就两处都写：

1. **先只在工具定义里写描述**，system prompt 里不列工具清单。
2. 跑一批 trace，看 LLM 会不会调错工具。
3. 只有确实调不对，才在 system prompt 里加**调用模式**（什么场景该调哪个工具）。
4. 无论哪种方式，**绝对不允许两处信息冲突**，也不允许一处提了某个工具、另一处不提。

![p024 10:33 讲师讲工具描述：主要问题是引用不一致，先靠工具自身描述](images/p024_0633s.jpg)

### Stage 9：上下文预算与 chunk 策略

**Step 9.1 定预算。** 常规任务：上下文占用不超过标称窗口的 **70%**。变长输出任务（要从文档里抽所有实例、要对每个词给注意力）：有效窗口是标称窗口的 **35%**。实践上按页数卡：**一个 prompt 不超过 50 页 PDF**。

**Step 9.2 切 chunk 按领域单元切。** 找领域专家会怎么切：一页、一节、一个站点地图条目。做完切分后做一次数据分析，看这个粒度合不合理。

**Step 9.3 长文档加 metadata 增强。** 为每份文档抽 metadata（摘要、目录、文档类型等，可用 LLM 抽），然后把这份 metadata 附加到该文档的**每一个 chunk** 上。原则是**先扩张，再删减**。

![p024 13:47 讲师讲 chunk 要按页与章节等领域的自然单元来切](images/p024_0827s.jpg)

### Stage 10：错误降不到零时，把 guardrail 放进关键路径

按成本从低到高排：

1. **确定性检查**（比如 device ID 必须来自给定集合）。最便宜，直接在生产里改。
2. **近似的代码 guardrail**（检查答案里每个词是否出现在工具输出里）。便宜，但要先对它本身做 eval。
3. **微调一个小模型**（讲师举例 BERT 风格的分类器），需要几千条标注样本，服务起来很快。
4. **把 LLM judge 放进关键路径**。讲师说他没怎么见人这么做，问题在成本和延迟。

无论用哪种，用户侧的体验都是同一套话术：界面显示「我们还在思考 / 正在检索更多信息」，实际在自我纠正。

![p024 17:02 讲师讲 guardrail 被触发时的用户侧话术：显示仍在思考，实际在自我纠正](images/p024_1022s.jpg)

### Stage 11：工具选型——先把「数据库」和「应用」分开

讲师的做法是把现成平台（Braintrust、LangSmith、Phoenix）**只当数据库用**，所有自定义分析、标注界面、报告都建在它上面，读写它。理由有两个：留一个逃生出口（有人要界面就把平台 UI 给他），以及数据可以拿去做后处理或后训练。

代价是每家 schema 都不一样，所以要写一层转换。讲师自己就写了这样的库（他提到一个叫 Lang Free 的、针对 LangSmith 的转换库），并且说这些工具比较糙，建议别人自己 vibe code 连接器。

![p024 05:41 讲师讲把 LangSmith / Phoenix 这类工具只当数据库、应用层自建](images/p024_0341s.jpg)

### Stage 12：零到一、没有生产数据的项目

讲师给的顺序是：

1. **先把预期设好**：上线前不可能证明 100%。
2. **尽快把生产数据飞轮转起来**，拿真实数据做错误分析，为每个 failure mode 建 judge。
3. **用位置做假设**：长文档中间的信息比两端难推理，可以先怀疑位于中段的字段。
4. **合成数据只用来验证假设，不要用来猜失败模式**。讲师明确说这可能是 overkill——「你不想把太多精力花在假设的失败模式上，而资源本可以花在别处、去修真实存在的错误」。

### 4.2 进场顺序决策表（Stage 0 的填法）

| 你的情况 | 先进场的是 | 讲师给的理由 |
|---|---|---|
| 你在这个领域做了很多年，熟悉常见错误 | **failure mode**（先列你预期会看到的错误） | "我可能先从我熟悉的那些错误开始——也就是我预期会出现的错误，而不是先想 persona。" p023 [11:36] |
| 你对这个 LLM 任务没有直觉 | **persona**（先想清楚用户是谁） | "如果你让我去做一个食谱聊天机器人，我会先从 persona 开始。" p023 [11:36] |

填完之后紧接着回答第二个问题：**persona 从哪来。** 讲师的口径是「真实也是一个光谱」——真人产生的 trace 就算真实，这个人可以是同事扮演。但**persona 名字本身可以让 LLM 来分**：拿 LLM 给已有 trace 打 persona 标签，用它帮你抽样、帮你做错误分析；如果分得够准，还能直接当 router 用。

### 4.3 数据模型草案（课里没有代码，以下为示意）

下面的表结构是为了把 Stage 2–5 的四样东西落下来：trace、failure mode、judge 判定、人工标注。**字段名是本文件自定义的**，不是课程输出，也不是任何平台的 schema。

```sql
-- 课里没有代码，以下为示意。字段名自拟，按自己的场景改。
PRAGMA journal_mode = WAL;   -- 允许一边读一边写

CREATE TABLE IF NOT EXISTS trace (
  trace_id      TEXT PRIMARY KEY,
  created_at    TEXT NOT NULL,          -- ISO 时间
  persona       TEXT,                   -- LLM 分类结果，可为空
  region        TEXT,                   -- 分层维度之一
  user_type     TEXT,                   -- 分层维度之一
  product       TEXT,                   -- 分层维度之一
  input_text    TEXT NOT NULL,
  output_text   TEXT NOT NULL,
  tool_outputs  TEXT,                   -- JSON 数组，guardrail 近似法要用
  source        TEXT NOT NULL           -- 'prod' | 'colleague' | 'synthetic'
);

CREATE TABLE IF NOT EXISTS failure_mode (
  fm_id         TEXT PRIMARY KEY,       -- 如 'fm_hallucinated_answer'
  name          TEXT NOT NULL,
  definition    TEXT NOT NULL,          -- 一句定义
  positive_ex   TEXT,                   -- 正例 trace_id
  negative_ex   TEXT,                   -- 反例 trace_id
  worth_eval    INTEGER NOT NULL        -- 0/1，Stage 3 分诊结果
);

CREATE TABLE IF NOT EXISTS judge_run (
  run_id        TEXT PRIMARY KEY,
  trace_id      TEXT NOT NULL REFERENCES trace(trace_id),
  fm_id         TEXT NOT NULL REFERENCES failure_mode(fm_id),
  judge_version TEXT NOT NULL,          -- prompt 版本号，改 prompt 必须升版本
  verdict       TEXT NOT NULL,          -- 'pass' | 'fail'
  rationale     TEXT
);

CREATE TABLE IF NOT EXISTS human_label (
  trace_id      TEXT NOT NULL REFERENCES trace(trace_id),
  fm_id         TEXT NOT NULL REFERENCES failure_mode(fm_id),
  labeler       TEXT NOT NULL,
  verdict       TEXT NOT NULL,          -- 'pass' | 'fail'
  PRIMARY KEY (trace_id, fm_id, labeler)
);
```

> 说明：在 Node 里如果直接用 `better-sqlite3`，它的 API 是同步的，写操作天然串行，不会出现两个写事务打架；如果用异步驱动或在多进程里跑标注任务，就要么把写入收敛到一个队列里，要么改用 Postgres，否则会撞上 SQLite 的写锁报错（`database is locked`）。**课里没讲**这块。

### 4.4 上下文预算表（Stage 9 的算式）

讲师给的是**百分比**（70% / 35%）和一个**页数上限**（50 页 PDF）。把百分比落成 token 数要自己算，标称窗口用你实际调的模型填：

| 任务类型 | 占用上限 | 标称 128k 时的有效上限 | 标称 200k 时的有效上限 | 讲师原话依据 |
|---|---|---|---|---|
| 常规任务（问答、摘要、判断） | 标称窗口 × **70%** | 128,000 × 0.70 = **89,600** | 200,000 × 0.70 = **140,000** | "我通常会把上下文窗口的使用上限控制在 70%。" p024 [11:43] |
| 变长输出（抽全所有实例、逐词给注意力） | 标称窗口 × **35%** | 128,000 × 0.35 = **44,800** | 200,000 × 0.35 = **70,000** | "我的有效上下文窗口是标称窗口的 35%。" p024 [11:43] |
| 文档类输入（按页卡） | **≤ 50 页 PDF / prompt** | — | — | "我不会放超过 50 页 PDF 在一个 prompt 里。" p024 [11:43] |

上表里的 token 数是按讲师给的百分比做的换算，**讲师本人没有给出具体 token 数字**，他只给了百分比和「50 页」这个页数口径。

### 4.5 judge prompt 模板（课里没有代码，以下为示意）

讲师没有当场念过一个 judge prompt 的全文，但 Stage 4/5 的流程要求每个 failure mode 对应一个判定器。下面这个模板是把「一句定义 + 一个正例 + 一个反例」的结构落成文本，**具体措辞需要你自己改**。

```text
# 课里没有代码，以下为示意。

你是一个严格的评审员。你只判断一件事：下面这段回答是否属于「{failure_mode_name}」。

失败模式定义：
{failure_mode_definition}

正例（属于该失败模式）：
{failure_mode_positive_example}

反例（不属于该失败模式）：
{failure_mode_negative_example}

判断规则：
1. 只依据上面给出的定义判断，不要引入其他标准。
2. 如果证据不足以判断，输出 unknown，不要猜。
3. 先写一句理由，再给判定。

待判定的对话：
<user>{input_text}</user>
<assistant>{output_text}</assistant>

输出格式（严格 JSON）：

```

关键约束只有一条：**改 prompt 就必须升 `judge_version`**，否则你没法回答「改了之后 prevalence 降了，是因为系统变好了还是因为 judge 变松了」。

### 4.6 两个可以直接跑的脚本：代码 eval + 近似 guardrail（课里没有代码，以下为示意）

讲师点名的「基于代码的 eval 像单元测试」和「95% 近似度的 guardrail」，本质是同一类东西：一段纯函数。下面用 Node 写，因为读者是前端背景。

**文件：`evals/code-evals/deviceIdAllowed.mjs`**

```js
// 课里没有代码，以下为示意。
// 用途：对应讲师说的「device ID 必须来自给定集合」这类确定性检查。

/**
 * @param {{deviceId: string}} toolCall  模型生成的工具调用参数
 * @param {string[]} allowed             允许的 deviceId 白名单
 * @returns {{ok: boolean, reason: string}}
 */
export function deviceIdAllowed(toolCall, allowed) {
  const id = toolCall?.deviceId;
  if (typeof id !== "string" || id.length === 0) {
    return { ok: false, reason: "missing_device_id" };
  }
  if (!allowed.includes(id)) {
    return { ok: false, reason: "not_in_allowlist", got: id };
  }
  return { ok: true, reason: "ok" };
}

/**
 * 把一批工具调用跑一遍，输出失败率。
 * 注意：这是「代码 eval」，不是 judge，结果可复现，不需要人工对齐。
 */
export function runDeviceIdEval(calls, allowed) {
  let failed = 0;
  const details = [];
  for (const call of calls) {
    const r = deviceIdAllowed(call, allowed);
    if (!r.ok) {
      failed += 1;
      details.push({ call, r });
    }
  }
  return {
    total: calls.length,
    failed,
    failRate: calls.length === 0 ? 0 : failed / calls.length,
    details,
  };
}
```

**文件：`guardrails/approximateGrounding.mjs`**

```js
// 课里没有代码，以下为示意。
// 用途：对应讲师说的「近似法 guardrail」——检查答案里每个词是否出现在工具输出里。
// 明确局限：这是近似，不是真值判断；讲师说它「可能不会把失败率降到零」。

/**
 * @param {string} answer        模型的最终回答
 * @param {string[]} toolOutputs 本次请求里所有工具返回的文本
 * @param {{minCoverage?: number, stopwords?: string[]}} opts
 */
export function approximateGrounding(answer, toolOutputs, opts = {}) {
  const minCoverage = opts.minCoverage ?? 0.9;
  const stopwords = new Set(opts.stopwords ?? DEFAULT_STOPWORDS);

  const corpus = toolOutputs.join("\n").toLowerCase();
  const words = tokenize(answer).filter((w) => !stopwords.has(w));
  if (words.length === 0) {
    return { grounded: true, coverage: 1, missing: [] };
  }

  const missing = [];
  for (const w of words) {
    if (!corpus.includes(w)) missing.push(w);
  }
  const coverage = 1 - missing.length / words.length;
  return { grounded: coverage >= minCoverage, coverage, missing };
}

function tokenize(text) {
  // 只做最小化处理：按非字母数字切，转小写。
  return String(text)
    .toLowerCase()
    .split(/[^\p{L}\p{N}]+/u)
    .filter((w) => w.length > 1);
}

const DEFAULT_STOPWORDS = [
  "the", "a", "an", "is", "are", "was", "were", "of", "to", "in", "on",
  "and", "or", "for", "with", "this", "that", "it", "as", "at", "by",
];
```

**这两个脚本必须自己先 eval。** 讲师的原话是「我会对这个基于代码的 guardrail 本身做 eval，看看它对你来说够不够好」——做法是拿一批有标注的 trace 跑它，看它和人工判定的一致率，再看它的延迟。**课里没有给一致率门槛，也没有给延迟上限。**

### 4.7 chunk 与 metadata 增强（课里没有代码，以下为示意）

对应 Stage 9 的 Step 9.2 / 9.3：按领域单元切，然后把文档级 metadata 附加到每个 chunk。

```js
// 课里没有代码，以下为示意。
// 输入假设：一份文档已经被按「页 / 章节 / 站点地图条目」切好了。
// 这个脚本只做「metadata 附加」，不做切分——切分粒度要你自己按领域定。

/**
 * @param {{docId: string, metadata: object, chunks: string[]}} doc
 * @returns {Array<{docId: string, chunkIndex: number, text: string}>}
 */
export function augmentWithMetadata(doc) {
  // metadata 建议包含：摘要、目录、文档类型、（案例场景下）案件级信息
  const header = renderMetadata(doc.metadata);
  return doc.chunks.map((text, i) => ({
    docId: doc.docId,
    chunkIndex: i,
    text: `${header}\n\n---\n\n${text}`,
  }));
}

function renderMetadata(md = {}) {
  const lines = [];
  if (md.docType) lines.push(`文档类型：${md.docType}`);
  if (md.summary) lines.push(`摘要：${md.summary}`);
  if (md.toc?.length) lines.push(`目录：${md.toc.join(" / ")}`);
  if (md.caseLevel) lines.push(`案件级信息：${md.caseLevel}`);
  return lines.join("\n"); // metadata 为空时返回空串，不污染 chunk
}

/**
 * 用来做讲师说的「一开始让 metadata 尽量扩张」：
 * 先全部打开，跑 eval，再看准确率决定删哪些字段。
 */
export function buildChunkSet(docs, { fieldsToKeep = null } = {}) {
  const out = [];
  for (const doc of docs) {
    const md = fieldsToKeep
      ? Object.fromEntries(Object.entries(doc.metadata).filter(([k]) => fieldsToKeep.includes(k)))
      : doc.metadata; // 默认全保留 = 「先扩张」
    out.push(...augmentWithMetadata({ ...doc, metadata: md }));
  }
  return out;
}
```

注意 `fieldsToKeep` 的默认行为：**默认全保留**。这是刻意按讲师那句「从 metadata 里删东西比往里加容易得多」来设的——先全给，跑出来准确率不行再按字段删。

## 5. 逐行解释

这一节按第 3、4 节的顺序，解释每条判断**为什么这样定、不这样会怎样**。所有数字都标了来源，凡是我自己算的都已注明。

**为什么「不要用 accuracy」这条要先讲。** 因为它是所有后续工作的前提。如果失败率 10% 你还在看 accuracy，你会看到一个 90% 的数字，然后得出「系统还行」的结论，于是根本不会去做错误分析。讲师把这个算式直接摆出来了：失败率 10% 时，一个永远输出 pass 的零模型 accuracy 就是 90%。也就是说，这个指标在这个分布下**区分不出「好模型」和「什么都不做的模型」**。换成什么？讲师没有指定单一替代指标，但语境里给了两个方向：一是用能反映失败的分母口径（按失败模式算 prevalence），二是在 RAG 场景用 hit rate。

**为什么分层抽样的判据是「业务重要性」而不是「数据量」。** 因为分层抽样解决的是「我要不要为这个维度单独建指标」，不是「我要不要让数据分布变均匀」。如果某个维度对你的业务根本不重要（比如某种极罕见的账号类型），它数据少也没关系；反过来，如果某个区域是你们主要收入来源，只占 5% 的数据也必须补到能算指标的样本量。这就是为什么讲师把问题表述成「这些维度在你的业务里是不是都重要」，而不是「数据够不够」。

**算例（我自己算的，讲师没给具体数字）。** 假设你总共只有 100 条 trace，三个区域占比是 A 70% / B 25% / C 5%，失败率大约 10%：

| 区域 | 占比 | 现在抽 100 条时有几条 | 按 10% 失败率能看到的失败条数 | 结论 |
|---|---|---|---|---|
| A | 70% | 70 | 约 7 | 勉强能看 |
| B | 25% | 25 | 约 2 | 太少，只能定性看 |
| C | 5% | 5 | 约 0.5 | **完全看不出失败率** |

C 区最需要分层抽样，因为按自然分布你几乎永远抽不到失败样本。补样本后要在表里明确写「C 区的指标是基于过采样算的，不代表线上占比」——否则汇报时会被人当成普适数字。

**为什么 Stage 3 要「先修再建 eval」。** 因为 eval 的建造成本包括写 prompt、人工标注、对齐、维护版本。讲师说的「低垂的果实」就是那些**修复成本远低于评测成本**的问题：代码 bug、明显的 prompt 笔误。给这类问题建 eval 是净亏——你花两天建了一个 judge，用来监控一个两小时就能修好且修完一眼可见的 bug。反过来，如果一个 failure mode 你已经反复改了三轮还没搞定，那 eval 立刻开始赚钱，因为你终于有了「改这一版到底有没有变好」的判据。

**为什么「基于代码的 eval」被单独夸。** 因为它不需要人工对齐：判定逻辑写在代码里，跑一百次结果一样，成本接近零，可以放进 CI。这就是讲师说它「更像代码里的单元测试」。分界线很清楚：**能用代码判的，别用 judge；只能用语义判的，才上 judge。**

**为什么要在 judge 上「投资于信任」。** 因为 judge 的价值全部来自「你敢不敢把它放到无标注数据上」。一个一致率不明的 judge，你只能拿它做参考，不能拿它做决策；一个你验证过的 judge，可以覆盖全量 trace，于是你从「100 条样本」跳到「几千条全量」，prevalence 才有统计意义。这就是讲师把它和错误分析并列为 ROI 最高的两件事的原因。

**为什么一致率 90% 只能当参考起点。** 那是学员在自己项目上报的数字，讲师回应的是「你这个做法不冲突」，**没有说 90% 是门槛**。而且一致率本身有陷阱：如果 95% 的样本都是 pass，一个永远输出 pass 的 judge 也能有 95% 一致率——和 accuracy 那个坑一模一样。**课里没讲**一致率该怎么算才稳健（比如要不要看 fail 类上的召回、要不要看混淆矩阵），这块要自己补。

**为什么改进回路要「第二个 LLM 只看 fail」。** 因为你希望改进建议集中在真正坏的地方。把全部 trace 丢给 LLM 让它「提改进建议」，它会花大量篇幅表扬你已经做对的部分，产出一堆不可执行的空话。只喂 fail 的 trace，它的输出天然对齐你的目标函数。讲师强调了这一步之后**必须人读**：「然后你读一遍，看看哪些讲得通。」——LLM 提的建议里必然有跑偏的，这一步不能自动化。

**为什么对外报「复合全局错误率」。** 因为干系人要的是「我们的系统大概多可靠」，不是「failure mode 7 的 prevalence 是 3.2%」。讲师的做法是保留多个 judge 做内部分析，对外合成一个「是否存在任何一种错误」的指标。同时要准备好被问「怎么知道这个数准」，答案模板是「我们和人工标注做过对比」——所以 Stage 4 的人工标注工作不只是为了调 judge，它还是你汇报时的证据基础。

**为什么热点问题要单列。** 讲师用「新闻业」打比方：如果所有人当下都在担心某类错误，把它藏在复合指标里等于在沟通上自杀。复合指标是给「总体健康度」用的，热点问题是给「安全感」用的，两者不能互相替代。

**为什么「错误降到零成本无限」这个说法有用。** 它是一个谈判工具。当干系人问「为什么不是 0」，你不需要辩解技术难度，只需要把问题转成资源分配：压某一个 failure mode 到零需要多少投入、代价是其他轴可能恶化、以及可能冒出没见过的新失败。然后问题自然变成「我们优先投哪个」，这就从对抗变成了共同决策。

![p024 15:25 讲师讲「把错误降到零的成本是无限的」，只能逼近零这个极限](images/p024_0925s.jpg)

**为什么 RAG 要先分诊。** 因为「生成问题」和「检索问题」的修复手段完全不重叠：检索问题要修索引、修切分、修召回；生成问题要修 prompt、修上下文组织、修输出约束。不先分诊就动手，你会在错误的层面上优化几个月。讲师那个案例里，团队一直在抱怨「答案不好」，错误分析后发现知识库根本没被索引——这是最典型的分诊失败：修一百遍 prompt 也不会有任何改善。

**为什么在命中数被硬限制时改用 hit rate。** precision / recall 衡量的是「你召回的集合相对正确答案的质量」，但当系统物理上只能塞 7 篇文档时，真正的产品约束是「7 篇里有没有」。这时候 recall 的分母（库里所有相关文档）对你的产品没有意义——你不可能把它们都放进去。hit rate 直接对齐产品约束，这就是讲师说「你可能得跳出 precision、recall」的实际含义。

**为什么工具描述先只写在 schema 里。** 因为两处都写会引入不一致的风险，而不一致是讲师点名的「主要的不要」。工具在 schema 里描述、system prompt 里不列，只有一处真相源；等你发现模型调不对工具，再在 system prompt 里加**调用模式**（什么条件下该调哪个），这时加的是策略而非清单，冲突面小得多。

**为什么 70% / 35% 要分成两档。** 因为这两类任务对上下文的敏感度不同。常规任务里，模型只需要从上下文里取一部分信息做判断，留 30% 余量足够；变长输出任务要求模型对上下文里**每一个词**都给注意力（抽全所有实例、逐条推理），这时上下文里的噪声会直接变成漏抽或错抽，所以要压到 35%。这是把「性能衰减」这件事量化成了一个预算约束。

**为什么还要有「50 页」这个页数上限。** 因为 token 数不可直观推理——讲师引述 Shreya 的说法：没人知道 200 个 token 是什么感觉，得换算成字符或词。而页、章节、站点地图条目是领域专家本来就在用的单位。用页数卡上限，你能直接和业务方对话（「这份合同 80 页，超了」），用 token 卡上限则不行。

**为什么 chunk 要按领域单元切。** 因为 chunk 的边界决定了检索和推理的边界。按逗号递归切会把一句话切成两半，模型拿到半句话，任何 judge 都会判它答非所问——但这其实是你切分造成的假失败。按页 / 章节切，切出来的每个单元至少是「人能读懂的一段完整意思」，错误分析时才不会把切分噪声误判成模型能力问题。讲师对 LangChain 那三十来种 splitter 的吐槽，本质是反对「不看数据就套默认切分器」。

**为什么长文档要给每个 chunk 附加文档级 metadata。** 因为很多信息不属于任何单个 chunk，但每个 chunk 的推理都依赖它。讲师举的两个例子：法庭记录里的案件级信息（每个 chunk 都要知道这是哪个案子），病历里的出院小结（整份文档的结论）。如果只把出院小结单独放一个 chunk，那你在看某一天的 progress note 时就没有全局背景了。所以做法是把文档级 metadata 附加到**每一个** chunk 上。

**为什么 metadata 要「先扩张再删减」。** 这是成本不对称：加 metadata 你要重新抽、重新跑 eval、重新验证；删 metadata 你只需要改一个过滤条件重跑。所以起步阶段把能抽的全抽上（摘要、目录、文档类型、结构化表格、过敏史等），如果准确率低到疑似被脏上下文拖累，再按字段逐项关掉。反过来做（先给最小集，不够再加）你要经历多次「加 → 重跑 → 还是不够 → 再加」的循环，慢得多。

**为什么 guardrail 要按成本排优先级。** 因为关键路径上的每一次检查都要乘上 QPS。确定性检查是纯 CPU 的字符串比对，成本接近零；近似代码 guardrail 是一次分词 + 查表，也很便宜；小模型要一次前向，但模型小所以快；LLM judge 是又一次完整的 API 调用，延迟和钱都是数量级差异。讲师明确说「把错误降到零的成本是无限的」，所以工程上要做的是**在成本曲线上找拐点**：先用最便宜的把最常见的一批错误拦掉，剩下的再考虑贵的。

**为什么用户侧话术要设计。** 因为拦截 + 重试意味着用户要多等几秒。如果界面上什么都不说，用户会以为卡死了然后刷新；如果显示「我们还在思考 / 正在检索更多信息」，同一段等待就变成了「系统在认真工作」。这是纯产品层面的设计，但它决定了你能不能在关键路径上放 guardrail——**课里没讲**具体文案怎么写、要不要给进度条。

**为什么把平台「只当数据库」。** 因为评测的形态高度依赖具体任务，通用平台必然要做抽象，抽象就会限制你。把它退化成存储层之后：数据仍是集中的（团队可共享），但分析逻辑、标注界面、报告全部由你控制。副产品是数据可以自由导出做后处理或后训练——这在平台的专用格式里很难做。代价是你得维护一层 schema 转换（讲师自己写了 `Lang Free` 这类转换库），而且平台改 schema 时你要跟着改。

## 7. 课里没讲但你会撞上的

下面这些是照第 3 节做下来**一定会碰到、但这两节课没给答案**的问题。每条都写清「撞上时的现象」和「可以怎么自己定」，并明确标注哪些是课里没讲的。

**7.1 一致率怎么算才不会被分布骗。** 现象：judge 和你的一致率 95%，你以为很好，结果它在全量数据上的 fail 判定和你的直觉完全不一致。原因和 accuracy 那个坑同源——样例里 pass 占绝大多数。课里没讲怎么处理。可以自己补的做法：分别算 fail 类上的召回和 pass 类上的召回，两者都看；或者直接看混淆矩阵，别只看单一一致率数字。

**7.2 100 条样本在你这个领域够不够。** 讲师提的例子是 100 条，但那是「没那么让人崩溃」的量级，不是标准。现象：你抽了 100 条，failure mode 长出了 40 个，每个只有两三条。这时候的解法不是继续抽，而是先把 40 个合并成 5–8 个大类。课里没讲合并规则，自己定：按「修复手段是否相同」合并，而不是按「描述是否相似」合并。

**7.3 分层抽样之后怎么加权回线上。** 现象：你补了 C 区的样本，重算出来失败率 18%，但线上实际是 12%。因为你过采样了高风险区域。课里没讲加权公式，只讲了「要分层抽样」。自己补的做法：分别算各区失败率，再按线上占比加权平均，报加权后的数字，同时在附录里放分区数字。

**7.4 平台 SDK 的具体写法。** 讲师提到了 Braintrust、LangSmith、Phoenix，也提到了他自己写的 `Lang Free`，但**没演示任何一个 API**、没给任何 SDK 调用代码、没说版本号。现象：你按第 4 节的表结构建了库，但要把数据同步到平台时不知道字段怎么映射。这块只能查各家文档，并自己写一层转换（见 4.3 说明）。

**7.5 judge 的成本在量级上是什么样。** 讲师说「evals 不是免费的」，但没给任何单价、token 估算或并发方案。现象：你把 judge 从 100 条扩到 3000 条，账单和耗时都可能超预期。自己补的做法：先做一次 100 条的计时和花费测量，线性外推到全量，再决定是不是要给 judge 加缓存（同一 trace + 同一 judge_version 结果可复用，这个幂等键用 4.3 里的 `run_id` / `judge_version` 就能实现）。

**7.6 guardrail 的重试上限与降级路径。** 讲师讲了「用户看到转圈，实际在自我纠正」，但没说重试几次、超时多久、重试仍失败时给什么。现象：你放了 guardrail 到关键路径，某个请求陷入重试循环，用户等了 40 秒。自己补的做法：定死重试次数（比如 1 次）、定死总超时、失败则降级成保守回复（例如「我暂时查不到，转人工」）。

**7.7 近似 guardrail 的假阳性。** 现象：4.6 里那个 `approximateGrounding` 会把合理的改写判成幻觉——模型说「设备已离线」而工具输出里写的是「状态：离线」，词对不上。讲师明确说这是近似，但没给处理方案。自己补的做法：放宽到词干/相似度匹配、或者对每个 failure mode 单独调 `minCoverage`，并且——按讲师的原则——**先对它本身做 eval，看假阳性率能不能接受**。

**7.8 metadata 的抽取成本。** 700 页病历、几千页案件卷宗，每份都要抽摘要 + 目录 + 类型。课里没讲这个抽取本身怎么控成本，也没讲要不要缓存。现象：抽 metadata 的钱可能比推理还多。自己补的做法：按文档类型分级（出院小结必抽，progress note 只抽首段），并且把抽取结果持久化（4.3 里可以加一张 `doc_metadata` 表）。

**7.9 SQLite 之外的选择与并发。** 讲师说他用「本地 SQLite + notebook」，那是个位数人团队的场景。现象：团队三个人同时在标注，写冲突频发。在 JS/Node 里对应什么：如果用 `better-sqlite3`，它是同步 API，单进程内写入天然串行；但多进程或多台机器就会撞 `database is locked`。解法是把写入收敛到单一服务（一个小的写队列），或直接换 Postgres。**课里没讲**这块。

**7.10 token 数怎么真的数出来。** 4.4 表里的 token 是我按百分比换算的，但真实计数依赖 tokenizer。课里没讲用什么工具数。现象：你以为 44,800 token 的上下文，实际算出来超了。自己补的做法：用对应模型的 tokenizer 做一次实测，把「页数 → token」的换算系数在你的文档类型上标定一次（扫描版 PDF 和结构化 PDF 差别很大），之后就用页数做预算。

**7.11 多轮对话重放时的状态复原。** 讲师讲了「从真实 trace 起、构造 starter conversation 复现错误状态」，但没说工具返回、检索结果、session 状态怎么一起复原。现象：你只重放了用户输入，模型这次没出错，因为上次的错误是由某次工具返回触发的。自己补的做法：把工具输出一起存进 trace（4.3 的 `tool_outputs` 字段就是为此留的），重放时一并注入。

**7.12 persona 分类的准确率怎么验证。** 讲师说「LLM 分类通常够好」，但没给验证方法。现象：你把 persona 当 router 用，被分错的那批用户落到了错误的处理路径上。自己补的做法：先人工标 50–100 条做验证集，算每个 persona 的精确率；只有精确率够高才允许当 router，否则只用来做抽样辅助。

**7.13 「文档中段更难」这个假设怎么验证。** 讲师给了这个假设，也提醒合成数据可能 overkill。现象：你花两周造合成数据验证它，最后发现中段失败率高是因为那几节本来就更难。自己补的做法：先在真实数据里按字段位置分组算失败率（零成本），只有真实数据确实显示位置效应、且样本量不足时，才考虑补合成数据。

**7.14 缺少一个官方仓库。** 这两段答疑里没有给出任何可 clone 的项目、`package.json`、依赖版本或启动命令。如果你想「照着跑完整项目」，**课里没讲**这个项目的代码；本文件第 4.5–4.7 节全部标注为示意，可以自己建目录跑起来：建一个 `evals/` 放 4.6 的两个脚本，用 `node --test` 或任意 runner 跑，`guardrails/` 放近似检查，`data/` 放 SQLite 文件。这几步是本文件为可复现性补的，不是课程内容。
