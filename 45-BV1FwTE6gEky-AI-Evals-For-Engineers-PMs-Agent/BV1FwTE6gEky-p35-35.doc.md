## 1. 这一节做什么

这一集是一次炉边对谈。课程主讲人请来了 Omar——他是 MIT 即将入职的助理教授、ColBERT 的作者、DSPy 的主导者——围绕"AI 工程到底是什么""DSPy 到底在做什么""评测在外循环里扮演什么角色"聊了一整集。

**这一集没有终端命令，没有代码演示，没有配置文件。**所以本文档不按"知识点流水账"来写，而是按纯讲解课的可复现方式处理：把讲师的推导过程摊开成一条**能照着走的工程流程**（第 3 节），把讲师给出的判断落成**四张可直接套用的表**（设计决策表、组件职责表、接口/数据模型草案、迭代预算估算表，第 4 节），再逐条解释每个决策为什么这么定（第 5 节）。

对前端转 AI 应用工程师的读者，这一集真正值钱的地方不是"学一个库"，而是拿到一套**判断程序**：什么时候该写最短的那一行、什么时候该加结构、什么时候该加工具、什么时候该跑优化器、什么时候该停手。这套判断直接决定你的 eval 集长什么样、你的 prompt 里该放什么、哪些东西该进代码仓库、哪些不该。

先说清楚边界：**课里没讲**任何具体的 DSPy 版本号、安装命令、API 签名和目录结构。第 4 节出现的所有代码都是**示意**，我会在代码块里显式标注；示意代码里的类名和写法请以你安装的 DSPy 版本的官方文档为准，不要拿它当"课里教过"。

## 3. 从零复现

这一节把讲师的推导过程还原成一条能照着走的流程：**需求 → 约束 → 估算 → 方案 → 取舍**。每一步都写清楚"做到什么算做到了"。

### 步骤 0：先给问题分类，这一步决定整条流程的长短

讲师明确把外循环分成两种极端情况：

- **类型 A：有公认数据集的问题。**比如你在写论文、提一个新方法、要在一个医疗问题的 benchmark 上证明现代大模型能做事。这时数据集存在，而且数据集本身就是被接受的 ground truth。讲师原话是"理解之沟和认知之沟在这个特定场景里没那么紧迫"。但你仍然要看数据、仍然要做错误分析。"如果数据集是错的，那没办法，它仍然是 ground truth。"
- **类型 B：用户高度主观、你根本不懂他们要什么。**讲师拿 Chatbot Arena 举例：用户非常有主见，你很难把他们全部的反馈收集齐，于是"巨大的一部分工作就是理解那件事本身"。

**做出来的标志：**你能用一句话说出你这条线属于 A 还是 B，以及如果你选了 A，你的 ground truth 是什么文件。

### 步骤 1：需求——先把外循环的问题问对

讲师给的外循环问题非常朴素，就三句：

1. 利益相关者到底想要什么？
2. 我能为这件事写出的**最短**的程序是什么？
3. 我用这个任务**负担得起的最大模型**跑一遍，会怎么崩？

在 DSPy 语境里，第 2 步常常就是"一行"：这里是输入，这里是输出，套一个思维链，看看大模型能干出什么。讲师强调"反正只有一步，很便宜"。

**做出来的标志：**你有一条能跑通的、只有一个模块的最简程序，并且你**真的读过它的输入和输出**。讲师对行业的抱怨是"大多数人连自己 prompt 里写了什么、输出长什么样、输入是什么都不知道，就想直接跳到 prompt 优化"。

### 步骤 2：约束——把四件事写进项目文档

1. **模型会换。**这是最基本的约束。你的规格如果依赖某个模型的具体怪癖，换模型那天就全废。
2. **你没有大规模训练数据。**讲师说至少 40% 的用户从没用过优化器，因为没有数据集，而他说这完全没问题。
3. **成本。**你要能回答"这个任务能负担的最大模型是哪个"。大模型不是问题，但你要知道自己在付什么。
4. **可维护性。**代码要交给别人，或者交给半年后的你。

**在 JS/Node 里对应什么：**第 4 条对你尤其重要。你的"程序"最终是仓库里的一堆 `async function`，同事会 review 它。一段被优化器调出来的、夹着 emoji 的 prompt 字符串，和一段有类型、有 docstring、有单测的函数，在 code review 里完全是两码事。

### 步骤 3：估算——把你的 eval 预算算出来

讲师没给具体金额，但他给了一个可以直接当锚点的数字：**100 个你信得过的数据点**。围绕这个锚点，把你的预算按下面的算式填满（公式是我按课程给出的结构拟的，具体数字你自己填）：

```
单轮全量评测成本 = 评测集条数 × 每条运行次数 × 单次调用成本
单轮全量评测耗时 = 评测集条数 × 每条运行次数 × 单次调用延迟 / 并发度
优化器运行成本   ≈ 单轮全量评测成本 × 优化器内部采样轮数
一次"换模型验证" ≈ 单轮全量评测成本
```

三条经验值直接来自讲师：

- 评测集的**最低可用规模**：约 100 条（讲师原话「100 个你信得过的数据点」）。
- 一次优化器运行的时间单位是**一晚**（讲师原话「跑一晚上，或者一边干别的活一边跑」）。
- 换模型验证是**廉价操作**——前提是你已经有数据集。讲师说他"一直用 GPT-5，好奇 Nano 行不行，就直接测 Nano，因为这时候我已经有数据集了"。

**做出来的标志：**你能在表格里填出"我每天最多能承受 N 次全量评测"，并且这个 N ≥ 1。

### 步骤 4：方案——把升级路径画出来（这是整集最核心的一条）

讲师给的是一条**严格的升级顺序**，从最简到最复杂，每一步都有明确的触发条件。我把他的话整理成下表的顺序（第 4 节有完整版）：

1. **一行签名。**最短签名 = 输入 + 输出 + 思维链。用负担得起的最大的模型。
2. **变成类 + docstring。**把一行签名升成类，好在 docstring 里写指令。
3. **加结构。**给字段加结构、加字段描述，必要时引入 Pydantic 类型。
4. **拆模块。**开始把一个模块拆成多个。
5. **换成 ReAct agent。**给它一堆工具。理由是"我不知道正确的结构，而 ReAct agent 比手工拆解更抗未来变化，因为它能替我选择"。
6. **换成手工工作流。**触发条件是：你发现系统不知道怎么按正确顺序用工具，而你心里有正确顺序。
7. **跑优化器。**触发条件是：程序跑得差不多了，并且我有了数据集（或者数据集在迭代中自己长出来了）。

注意第 5 步和第 6 步**可以反向走**——讲师说"有时候是反过来的，有时候你就是从工作流开始，取决于问题"。

### 步骤 5：取舍——什么该进代码，什么不该进

讲师对"什么该被维护"这件事极其明确：

- **该进代码的：**控制流（谁调谁、谁能看到什么）、结构化输入输出、意图（docstring 里的英文）、eval 集。
- **不该被当成资产维护的：**为了讨好某个特定模型而调出来的 prompt 花活。讲师原话是"因为它帮了 GPT-4，未必帮 GPT-5；帮了 Claude，未必帮 Llama"。

所以取舍规则是：**任何"不知道为什么有效"的改动，都不许独自留在代码里；它要么被 eval 证明有效并写进规格，要么被记进一个可丢弃的适配层。**

```ts
// src/pipeline.ts
// 课里没有代码，以下为示意：把讲师的七级升级路径落成同一份文件里的七个阶段。
// 注意：这不是 DSPy 的 API，DSPy 是 Python 框架；这里只是把它的"分层思想"翻译成 TS。

/** 注入点：真实项目里换成你的模型 SDK 调用。签名固定，方便后面整体替换。 */
export type ModelCall = (args: {
  instructions: string;      // 对应 docstring 里那段英文：我想要什么
  input: Record<string, unknown>;
  outputFields: FieldSpec[]; // 对应 signature 的输出字段声明
}) => Promise<Record<string, unknown>>;

export interface FieldSpec {
  name: string;
  desc: string;
  type?: 'string' | 'number' | 'boolean' | 'string[]';
}

// ---------- 阶段 0：Adapter 层（对应讲师说的"99% 的用例不用管它"） ----------
// 职责：把结构化对象物化成模型能吃的具体形式，并把结果解析回对象。
// 它不承载业务意图，所以可以被整体替换（JSON <-> XML <-> 别的）。
export interface Adapter {
  format(instructions: string, input: Record<string, unknown>, outputs: FieldSpec[]): string;
  parse(raw: string, outputs: FieldSpec[]): Record<string, unknown>;
}

export const jsonAdapter: Adapter = {
  format(instructions, input, outputs) {
    return [
      instructions,
      `INPUT: ${JSON.stringify(input)}`,
      `OUTPUT_FIELDS: ${JSON.stringify(outputs)}`,
    ].join('\n');
  },
  parse(raw, outputs) {
    const obj = JSON.parse(raw) as Record<string, unknown>;
    for (const f of outputs) {
      if (!(f.name in obj)) throw new Error(`missing output field: ${f.name}`);
    }
    return obj;
  },
};

// ---------- 阶段 1：一行签名（最短可行程序） ----------
// 讲师：最短签名就是"这里是输入，这里是输出，直接思维链，看看大模型能干出什么"。
// 用这个任务负担得起的最大模型；只有一步，很便宜。
export interface Signature {
  inputs: FieldSpec[];
  outputs: FieldSpec[];
  intent: string; // 这是文档，不是给模型的 prompt
}

export const oneLineSignature: Signature = {
  inputs: [{ name: 'text', desc: '待判断的原始文本', type: 'string' }],
  outputs: [{ name: 'isSpam', desc: '是否为垃圾信息', type: 'boolean' }],
  intent: '判断给定文本是不是垃圾信息。',
};

// ---------- 阶段 2~4：Module（吃对象、吐对象），结构、描述、拆解都发生在这里 ----------
export class Module<TIn extends Record<string, unknown>, TOut extends Record<string, unknown>> {
  constructor(
    private readonly sig: Signature,
    private readonly call: ModelCall,
    private readonly adapter: Adapter = jsonAdapter,
  ) {}

  async forward(input: TIn): Promise<TOut> {
    const raw = this.adapter.format(this.sig.intent, input, this.sig.outputs);
    // 真实实现里，这里把 raw 交给模型，再 parse；示意里用一个确定性桩函数顶替。
    const parsed = this.adapter.parse(
      JSON.stringify(stubModel(raw, input, this.sig.outputs)),
      this.sig.outputs,
    );
    return parsed as TOut;
  }
}

/** 示意用桩：不调用任何模型，只为让骨架能编译、能跑。 */
function stubModel(raw: string, input: Record<string, unknown>, outputs: FieldSpec[]) {
  void raw;
  const out: Record<string, unknown> = {};
  for (const f of outputs) {
    if (f.name === 'isSpam') out[f.name] = String(input.text ?? '').includes('中奖');
    else out[f.name] = `stub:${f.name}`;
  }
  return out;
}

// ---------- 阶段 5：把能力当"变换"叠加，而不是写进任务定义 ----------
// 讲师：signature 本身不知道什么是思维链，它是叠加在上面的。
export type Transform = (sig: Signature) => Signature;

export const chainOfThought: Transform = (sig) => ({
  ...sig,
  // 意图不变，只是在提示层面追加一步"先推理"。任务本体没有被污染。
  intent: `${sig.intent}\n先逐步推理，再给出结论。`,
});

export const withTools: Transform = (sig) => ({
  ...sig,
  intent: `${sig.intent}\n你可以调用提供的工具来获取外部信息。`,
});

// ---------- 阶段 6：工作流——当"顺序"本身是规格的一部分 ----------
// 讲师：我发现系统不知道怎么按正确顺序用工具，而我心里有正确顺序，于是换成拆解。
export async function runWorkflow(input: { question: string }) {
  const retrieve = new Module<{ question: string }, { docs: string[] }>(
    {
      inputs: [{ name: 'question', desc: '用户问题', type: 'string' }],
      outputs: [{ name: 'docs', desc: '检索到的文档片段', type: 'string[]' }],
      intent: '在私有语料里检索与问题最相关的片段。', // 固有复杂度：模型不可能知道的知识
    },
    stubCall,
  );
  const answer = new Module<{ question: string; docs: string[] }, { answer: string }>(
    {
      inputs: [
        { name: 'question', desc: '用户问题', type: 'string' },
        { name: 'docs', desc: '检索到的文档片段', type: 'string[]' },
      ],
      outputs: [{ name: 'answer', desc: '最终回答', type: 'string' }],
      intent: '只基于给定文档回答问题；文档里没有的不要编。',
    },
    stubCall,
  );
  const d = await retrieve.forward({ question: input.question });
  return answer.forward({ question: input.question, docs: d.docs });
}

const stubCall: ModelCall = async ({ input, outputFields }) => {
  const out: Record<string, unknown> = {};
  for (const f of outputFields) {
    if (f.name === 'docs') out[f.name] = ['stub doc 1', 'stub doc 2'];
    else out[f.name] = `stub answer for: ${String(input.question ?? '')}`;
  }
  return out;
};
```

**文件 2：`src/eval.ts`**（完整文件；`cases` 就是讲师说的"100 个你信得过的数据点"）

```ts
// src/eval.ts
// 课里没有代码，以下为示意：eval 集 + 单轮全量评测。
import { Module, jsonAdapter, type Signature } from './pipeline';

export interface EvalCase {
  id: string;
  inputs: Record<string, unknown>;
  expected?: Record<string, unknown>; // 类型 B 的问题里可能没有标准答案
  notes?: string;
}

export interface CaseResult {
  id: string;
  output: Record<string, unknown>;
  ok: boolean;
  note?: string;
}

export function runEval<TIn extends Record<string, unknown>, TOut extends Record<string, unknown>>(
  mod: Module<TIn, TOut>,
  sig: Signature,
  cases: EvalCase[],
): Promise<CaseResult[]> {
  void jsonAdapter;
  void sig;
  return Promise.all(
    cases.map(async (c) => {
      try {
        const output = await mod.forward(c.inputs as TIn);
        if (!c.expected) return { id: c.id, output: output as Record<string, unknown>, ok: true, note: 'no-expected(needs human)' };
        const ok = Object.entries(c.expected).every(
          ([k, v]) => JSON.stringify((output as Record<string, unknown>)[k]) === JSON.stringify(v),
        );
        return { id: c.id, output: output as Record<string, unknown>, ok };
      } catch (e) {
        return { id: c.id, output: {}, ok: false, note: String(e) };
      }
    }),
  );
}
```

## 5. 逐行解释

这一节逐条解释第 4 节每个决策、每张表里的每一行、以及示意代码每个分层为什么这么定。核心判据只有一个：**讲师反复强调的是"什么被保留下来、什么被丢掉"。**

**D1（三样东西缺一不可）。**讲师把"代码/控制流 + 自然语言规格 + eval"并列为一般情况下的必要条件。为什么控制流不能省？因为控制流承载的是一条**只有你知道**的信息——讲师在总结自己三段经历时说得很清楚："你在描述一个 AI 系统时拥有的信息流，是只有你知道的；还有上下文——现在人们可能叫它上下文工程——其实是非常应用特有的。"控制流就是"哪个模块能看到哪些东西"的显式声明。讲师甚至举了具体的例子："我希望这个模块能看到这些，但不要看到那些，因为它们跟它无关。"这句话在代码里就是一个参数传递边界，在 prompt 里是写不出来的。在 Node 里，它对应的是"这个函数收哪些参数"，而不是"我在 prompt 里叮嘱它别看别的"。

**D2（从一个模块起步）。**讲师的原话是"这跟流行观念相反"。流行观念是既然 agent 很火，就先架一个多 agent 编排。讲师反对的理由不是"简单更好看"，而是**信息论上的**：你还没有 eval、还没有错误分析，此时你拆出来的结构是猜的，而猜出来的结构一旦写进代码就会开始自我固化——后面所有优化都在这个错误结构上做。他还补了一句很关键的缓和："你从简单开始，从最简单、哪怕你觉得会失败的那个东西开始。"允许一开始就失败，是这个决策能成立的前提。

**D3（对象进、对象出，与模块定义分离）。**讲师点名批评了一种很常见的代码布局："拼字符串是一段、调模型是一段、解析是一段，三段分开写。"这种布局的问题不在于丑，而在于**耦合方向错了**：业务逻辑和"怎么讨好模型"被耦合在一起，而"任务是什么"和"输入输出长什么样"反而被拆散了。讲师说 DSPy 的做法是"Module 是一个函数，它吃对象、吐对象"，这句话在工程上的含义是：模型调用变成了一个**普通依赖**，你可以像换数据库驱动一样换它。对前端读者，这就是把 `fetch` 调用从组件里抽到一个 `apiClient` 里，只不过这里抽的是"意图 → 对象"的转换。

**D4（signature 不写 JSON/XML）。**讲师说得非常直接："你不会说给我 JSON，也不会说给我 XML。你的目标是拿回对象。"为什么？因为格式选择是一个**有代价的决定**，讲师在第 34:22 那段专门讲过这个代价：假设你用 JSON，因为"OpenAI 现在有结构化输出"；然后"你发现你在让模型写代码，而在 JSON 里写代码是出了名的难，因为模型得做各种 funny escaping"；于是你换 XML；然后"你还得解析这段 XML"。三个决定串起来，每一个都逼出下一个，而这些决定**都不属于任务本身**。把它们放进 signature，等于把你的任务定义写成"用 JSON 输出代码"，这是一个自相矛盾的规格。放进 adapter，它们就变成可替换的。

**D5（能力是变换）。**讲师举了两个例子：想加推理，"你只要给 signature 套一个思维链变换就行，signature 本身不知道什么是思维链"；想要 agent 加工具，"任务本身的职责不是知道自己是个 agent、有工具，它的职责只是翻译或者总结"。这条之所以重要，是因为它解释了为什么"模型换代"不该毁掉你的工作：CoT 是当年为了补模型短板加的装饰，模型自己会推理了（讲师调侃"现在因为某些原因模型本身就是推理模型了"），你把装饰摘掉就行，任务定义一个字都不用改。反过来，如果 CoT 写进了任务定义，摘的时候你就在改规格，而改规格要重新做 eval、重新对齐利益相关者。

**D6（docstring 是文档）。**这是全篇最反直觉、也最值得单独讲的一条。讲师的用户里"品味很好"的那批人提出了一个很好的抱怨：为什么重要内容要放在类的 docstring 里？讲师说这个抱怨"很美"，因为它给了他解释的机会："DSPy 程序里 docstring 的指令不是给语言模型的提示词，它们是给 DSPy 的指令，它们其实是文档——你在记录你想要什么。"接着他给出了一个具体的技术理由：模型对否定式指令很敏感，"我要是告诉它别说某些话，它反而会说，因为你提醒了它"，所以 DSPy 保留"不告诉模型、事后检查、必要时重采样"的权利。他还留了一个重要的免责声明：**"我不是说今天就在这么做，我是说这跟这个库的语义是一致的。"**这句话必须原样保留，否则读者会以为这是已落地的行为。对你写代码的指导意义是：docstring 里禁止出现"全大写""加 emoji""你是世界最好的专家"这类讨好模型的措辞，那些属于 adapter 或优化器的产物，可丢弃。

**D7（只在不满时才加复杂度）。**讲师把顺序钉死了："先加问题本身固有的复杂度，再跑优化器作为泛化之沟的第一手段，最后才加那些很可能明年 GPT-7 出来就被取代的 hack。"他同时说了一句很重要的话："没有保证优化器能完全解决问题——这就是为什么你是工程师，这就是为什么有人付钱让你处理这个问题。"所以这一步不是"优化器兜底"，而是"优化器先上，人再上"。

**D8（先加固有复杂度）。**讲师举的例子是私有邮件："它就是我的邮件，而且一直在变，它是私有的，模型不可能猜到。"这句话定义了什么是"固有"：**模型无论多大都不可能有**的信息。判断方法很简单——问自己"如果给我一个无限强的模型，它能不能答对？"能，那就不是固有复杂度，是优化问题；不能，那就先加工具/检索。这也正好接上他的三段总结的第一段：信息流是应用特有的。

**D9（优化器不是必需品）。**讲师给了 40% 这个数，并说"没有压力，你不需要，就不用"。他还用编译器做了个类比："我不确定我是否真的从 GCC/G++ 的优化器里受益，但我很舒服、很高兴。有的人有 SIMD、有很复杂的循环，想要花哨的优化；另一些人代码很简单，就是喜欢这个语言。"这个类比的落点是：**用不用优化器是风格选择，不是能力证明**。但注意，这不等于"不需要 eval"——讲师紧接着就把 eval 重新定义成"一个人坐下来、能看见失败、能在对的地方介入"，也就是说 eval 是**人和流程**，不是那个优化器输入文件。

**D10（换小模型要跑全量）。**逻辑很直白：换模型是分布变化，你必须用同一份数据集测。讲师的价值补充是"优化器对小模型的收益往往更大，因为提升空间大得多"——这意味着降本的正确顺序是"先换小模型 → 再跑优化器 → 得到便宜得多的系统"，而不是"先跑优化器 → 再换小模型"。

**表 C 各实体。**`SignatureSpec` 的 `intent` 字段是 D6 的落地；`FieldSpec.desc` 对应讲师说的"开始给字段加描述"；`type` 对应"需要的话引入 Pydantic 类型"（在前端世界就是 TS 类型或 zod schema）。`EvalCase.expected` 标成可选，是因为讲师明确区分了类型 A（数据集即 ground truth）和类型 B（没有公认答案，只能靠理解用户）。`Trajectory` 这个实体不是装饰：讲师讲 Baleen 时说的就是轨迹——"我希望系统成功检索到这篇文档，但我不知道它会走哪条路径，那我就奖励它做对；让系统跑，它做对了，我就把这条轨迹当作训练数据点。"这句话同时解释了为什么端到端 eval 在**没有中间步骤标注数据**时是必需的，而不只是方便。`OptimizerRun.specHash` 是我加的一道护栏，理由来自 D7：优化器不许改规格，只许改表达；如果一次"优化"改动了 specHash，那它不是优化，是重新定义任务，必须走一遍完整的外循环。

**示意代码各分层。**`ModelCall` 被写成注入参数，是为了让"换模型 = 换一个函数"这件事变成类型系统能保证的事；`Adapter` 单独存在，是 D4 的直接实现；`stubModel` 的存在是为了让读者**不装任何 SDK 也能先跑通骨架**，这也是讲师"从最简单、哪怕你觉得会失败的那个东西开始"的具体执行；`chainOfThought` 被写成 `Transform` 而不是写进 `intent` 常量，是 D5 的实现；`runWorkflow` 里"检索"那个模块的 `intent` 写的是"在私有语料里检索"，这就是 D8 的固有复杂度；`pickBest` 只挑配置、不改规格，并且在分数不升时回滚，这是"优化器产物必须可回滚"。

**一句必须点出的取舍。**讲师在最后用编译器类比收尾："你跑到 C++ 编译器面前说：我有一段不够快的汇编，你还我一段做同样的事但快得多的汇编，虽然它更绕更怪。然后你复制粘贴进去。就在那一刻，你失去了可移植性，也失去了可读性。"这段话解释了为什么"给我一段更好的 prompt"这个诉求在工程上是错的——它换来的东西**不能被维护**。而他对 emoji 的态度特别值得学："我们的反应常常是'这不可能有用'，但我的反应是：我不知道，可能真有用。"这是**认知上的谦逊 + 工程上的纪律**：不否认花活可能有效，但坚决不让它成为你要维护的资产。

## 7. 课里没讲但你会撞上的

这一节全部是**课外经验**，不是讲师说的，请当作"照着做时会遇到的路况"，不要当成课程结论。

**1. DSPy 的安装、版本与 API 签名：课里没讲。**
这一集从头到尾没有出现一条命令、一个版本号、一个函数签名。所以第 4 节的示意代码不能直接 `npm install` 跑，DSPy 本身是 Python 框架，你在 Node 项目里要用它得走子进程或 HTTP 服务。真正落地前，请以官方文档为准，并且**先把"分层"落地，再选"库"**——讲师讲的每一层（签名、模块、适配层、优化器、eval 集）在 Node 里都有手写等价物，不一定非要引入框架。

**2. "docstring 是给 DSPy 的文档"这句话有前提。**
讲师自己加了免责声明："我不是说今天就在这么做，我是说这跟这个库的语义是一致的。"所以你不能假设你安装的那个版本一定真的会"不告诉模型、事后检查、重采样"。落地时要么去文档里确认，要么自己在外层加一道后置检查（正则/分类器/再采样），别指望框架替你做。

**3. 类型 B 问题没有 ground truth，评测会一直"不收敛"。**
讲师把类型 B 描述为"巨大的一部分工作就是理解那件事本身"。这类项目的现实问题是：你的 eval 集会长期处于"有人工标注但标注者之间不一致"的状态。你会撞上的是标注冲突，而不是模型不行。处理方式课里没讲；实践中可行的是：把 `EvalCase.expected` 留空，把 `notes` 写成"这里人也没共识"，并把分歧本身当成待办。

**4. 优化器的成本会显著高于你预估的一次全量评测。**
讲师说"跑一晚上"，但没说优化器内部要跑多少轮。表 D 里的"优化器内部采样轮数"是最容易估错的一项。现实做法：先用 20~30 条做一次小规模试跑，量出单轮成本，再放大到 100 条。

**5. 优化器的可复现性。**
`OptimizerConfig` 里的 `seed` 是我加的，不是课程内容。真实优化器涉及采样，同一份输入跑两次可能得到不同的指令。你必须有 `specHash` + 版本号 + 完整配置的快照，否则半年后没人能解释线上那段 prompt 是怎么来的——而这恰恰是讲师最反对的状态（"没有任何地方被记录下来，你只剩一个技巧"）。

**6. 那些"可能真的有用"的 emoji 必须被隔离。**
讲师的态度是"我不知道，可能真有用"，但"它不该是你代码里要维护的东西"。落地时唯一的办法是：花活只允许出现在**优化器产物**或**可丢弃适配层**里，并且必须由 eval 分数支持；一旦 eval 不再支持它，就删掉。这条纪律的价值在换模型那天体现——你只需要重跑一次评测，而不是逐个猜哪些花活还有效。

**7. 前端视角的额外摩擦：并发与限流。**
你的 eval 集是 100 条，每条可能多次运行，这意味着你要在 Node 里控制并发。课里没讲并发模型；实践中你需要一个信号量（例如自己写一个 `p-limit` 风格的队列）以免打爆供应商的速率限制。示意代码里的 `Promise.all` 只适合小规模。

**8. 讲师提到但课里没展开的优化器种类。**
他点了四个名字：造 few-shot 示例、迭代指令、GRPO 强化学习、过滤式行为克隆；另外还有"找出高方差示例、把成功轨迹变成 few-shot"的那一类。他还提到"至少某一个 release 里会重写你的指令"，逐字稿这里写的是 JEPA，**很可能是 GEPA 的口误或转写误差**——这一点我不替你下结论，遇到时请以官方文档为准。这四类各自的适用场景、数据要求、失败模式，本集都没有展开，属于课里没讲。

**9. 讲师明确提到但未解决的开放问题。**
课程主讲人问了一个很好的问题：如果模型变得很强，我是不是该把 CoT 从管线里摘掉？那"我写好规格、模型换代我也不用改"这个愿景是不是太乐观了？讲师的回答是"这是需要对我说的所有话加保留的地方"——他没有给一个确定的边界，只说"作为工程师，我得擅长判断我要哪张草图"。这个问题课里没答案，你会在真实项目里反复撞上：抽象层能挡住多少模型换代，是一个要按项目逐个量的问题，不是一条可以背下来的规则。
