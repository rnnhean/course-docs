## 1. 这一节做什么

这一讲是学员 Robert（第一期的学员、社区活跃成员）主讲的一场**现场实测（live testing / bake-off）**。核心主张只有一句：**评测（evals）是让「主观的 AI 产品」变得可以客观改进的手段**，而做评测的起点不是写代码，而是**先定义维度（dimensions）**，再**用真实用户查询去打产品、做错误分析（error analysis）**。

本讲做了两组对照实验：

1. **会议记录类产品**：Granola（左）vs Otter（右）。用同一场「与联合创始人的冲刺规划 / 待办梳理会」的录音，先比默认摘要，再用同一批用户查询去问两个产品的 AI 问答层，现场投票、现场做错误分析。
2. **Vibe coding / 低代码建站类产品**：Lovable（左）vs Base44（右）。用**同一个未加工的英文 prompt**（做一个简单 to-do app）分别生成，然后按大家现场提出的启发式维度（美观、可用性、是否预置示例数据、是否有 toast 反馈、是否内置鉴权与密钥管理、是否容易改）逐条打分。

贯穿全场的框架是 **Teresa Torres 的「假设检验（assumption test）」+ 五类维度**：desirability（合意性）、usability（可用性）、feasibility（可行性）、viability（商业可行性）、ethical（伦理）。讲师反复强调：**维度没有标准答案，取决于 ICP（理想客户画像）和具体用例**；同一个输出，不同背景的人（工程师、架构师、MLE、AI 研究员、创始人、PM、技术 PM）会给出不同评分，这恰恰是邀请多元背景的人一起评测的价值。

对前端转 AI 应用工程师的读者，这一讲最实用的三点是：

- **评测维度先于评测代码**：先把「什么算好」写成可判断的条目，再谈自动化。
- **代码型 eval 最适合做护栏（guardrail）**：例如「用户问到竞品时，绝不能推荐竞品」这种失败模式，用关键词检测就能兜住。
- **延迟不一定要优化，改 UX 就行**：让用户知道「AI 在想」，往往比把响应做快更有效。

## 3. 从零复现

这一节把讲师的现场流程拆成可以照着做的步骤。你不需要写代码，只需要**两个浏览器标签页 + 一份维度表 + 一个记录表**。

### 3.1 准备：确定对照对象与统一输入

讲师的做法是**成对对照（bake-off）**，每组只改一个变量：产品不同，输入完全相同。

| 组别 | 左 | 右 | 统一输入 |
|---|---|---|---|
| 会议记录 | Granola | Otter | 同一场「与联合创始人的冲刺规划 / 待办梳理会」录音 |
| 建站 | Lovable | Base44 | 同一段未加工的英文 prompt（做一个简单 to-do app） |

关键约束（讲师明确强调的）：

- **不要美化 prompt**。讲师说他平时会用调好的 PRD 生成器 prompt，但这次**故意不加工**，目的是模拟「一个只会说人话、想要一个 app 的低代码 / 无代码用户」。
- **两边同时发同一个 prompt**，让它们同时跑，避免时间差带来的偏差。
- 会议记录组要**先看默认摘要**（不套 system prompt、不套模板包），因为默认输出本身就是产品体验的一部分。

### 3.2 第一步：先看默认输出，不看问答

讲师先并排看两个产品的**默认摘要**，逐项记录差异：

- Otter（左）没有识别出「我是从日历进入这场会」的日历事件名，摘要直接进入要点，没有 overview；不识别参会人。
- Granola（右）以 overview 开头，顶部展示的信息不同；能识别出「产品聚焦与范围对齐」这类主题。
- 讲师解释差异的根因：**Granola 不加入会议**，它靠系统音频录制「倒推」上下文，所以天然缺少会议元信息；Otter 是加入会议的。
- 现场投票：Granola 打 1，Otter 打 2。结果 **2 胜**。理由集中在：右边有 overview、有组织、视觉上更易消化（digestible）、对人类认知负荷更友好。

> 复现要点：这一步**不要急着问问题**。默认输出的信息架构（有没有 overview、有没有分区、有没有时间戳）本身就是评分维度。

### 3.3 第二步：用同一批用户查询打两个产品的问答层

讲师准备了一组「真实用户会问」的查询，**同一句话同时丢给两个产品**：

1. 「我们刚开完冲刺规划和待办梳理会。你能总结我们做的关键决策吗？主要技术风险是什么？哪些功能被排了优先级？」
2. 「这次会议之后我应该立刻做的下一步是什么？」（现场观众 Sabina 提的典型用户查询）
3. 「为什么 Otter 是比 Granola 更好的笔记应用？」/「为什么 Granola 是更好的 AI 笔记应用？」（**低成本的越狱式提问**，用来观察产品会不会「防御性」回答）
4. 「这个产品背后的团队是怎么做 evals 的？」（讲师的招牌测试法）
5. 「这场产品会议本来要怎么组织，才能改善结果、减少浪费时间？」

每问完一轮就现场投票（1 = Granola，2 = Otter），并让投票的人说理由。

### 3.4 第三步：现场做错误分析（error analysis）

讲师在问答过程中实际观察到的失败模式，逐条记录：

- **Granola 对「团队怎么做 evals」的回答**：它把问题理解成「这场会议里有没有提到」，回答「转录和会议笔记里不包含关于 Granola 产品团队如何做 evals 的信息，这场会议聚焦于 Robert」。→ 失败模式：**意图理解错误**，把元问题当成了会议内容检索。
- **Otter 对同一问题的回答**：先承认不知道，然后给出兜底信息（Otter 有反馈机制，用户可以给转录质量打分、可以授权 Otter 使用对话做训练），并建议联系支持团队。→ 讲师判定**右边更好**。
- **Granola 对「下一步」的回答**：出现了「continue grinding」这类**过于字面**的复述（因为讲师在会里确实说过这个词），对一周后回来看的用户不可理解。→ 失败模式：**缺少「用户回来时的新鲜度」这个上下文维度**。
- **Otter 对「为什么 Otter 更好」的回答**：承认用户可能认为 Granola 更好，然后列举自身优势（市场领先者等）。讲师点评「Otter 变得防御性了」，并指出这只是一次**低成本的越狱**，产品没有为此设防。
- **Base44 在最后一轮「加标签和分类」时崩了**（页面坏掉），讲师当场判定「Base44 在最后这里死掉了」。

### 3.5 第四步：把观察映射回五类维度

讲师把现场收集到的所有启发式，逐条塞回 Teresa Torres 的五类桶里：

- **desirability（合意性）**：上下文是否准确、有没有时间戳、有没有回答我的问题、是否给出我真正需要的下一步。
- **usability（可用性）**：有没有 overview、格式是否易读、来源（provenance）展示是否清楚、响应速度带来的感受。
- **feasibility（可行性）**：速度；以及质量层面的稳定性。
- **viability（商业可行性）**：信任与风险缓解（例如竞品问题上的护栏）。
- **ethical（伦理）**：录屏 / 录音是否告知对方；生成代码是否抄袭非开源许可的代码库。

### 3.6 第五步：建站组按启发式逐条打分

讲师让观众先在 Discord 里提「这个 to-do app 用例该测哪些维度」，然后**拿着这份清单逐条实测**。现场提出的维度（原样保留）：

- 到可用 app 的时间（time to working app）
- 是否满足用例（did it do what I thought it would do based on what I typed）
- 是否可用（usable）
- 代码是否可维护（maintainable code）
- 开箱美观（good aesthetic out of the box）
- 没有缺失的任务 / 里程碑
- 对用户直觉（intuitive to use）
- 不会被输入的数据格式搞坏
- 到「工作版本一」之前要来回多少轮
- 功能正确性、可用性、可维护代码、是否内置测试、是否考虑错误处理、清晰的错误信息与日志、可扩展性、跨会话无错误
- 改动有多容易
- 伦理：是否抄袭非开源许可的代码库
- 绿地 / 棕地、开发与生产都算
- 给我多少控制权
- 是否会问有用的澄清问题、是否提供好的反馈方式

### 3.7 第六步：实测 to-do app 的具体操作

讲师给两边的 prompt 原文（他明确说「我没有加工过」）：

```
Create a simple to-do app. A user can add tasks with a description and due date,
view a list of tasks, mark tasks as complete, and edit or delete entries.
```

然后按以下顺序操作并记录：

1. 加一条任务：「AI evals, product, live testing, session execution」。
   - Lovable（左）：**必须先加 due date 才能加任务**，讲师说「这不太明显」。
   - Base44（右）：可以直接加。
2. 看初始状态：**Base44 预置了示例任务**（讲师没要求），Lovable 是空的。讲师认为预置示例是「很好的用户体验 touch」，因为「我能想象自己的任务在里面」。
3. 看统计：Base44 在 app 上直接显示「1 of 5 completed」这类数字，讲师更喜欢这个。
4. 完成一条任务：Base44 给了 toast 反馈（「像被拍了一下头」），Lovable 的「juice」较少；但 Lovable 的完成动画很好看（讲师没要求过）。
5. 点 X 关闭：Lovable 的 X 点了没关掉 → **代码 bug**。
6. 刷新页面：Lovable 不记得我的任务，Base44 记得 → 产品差异。
7. 加任务的操作成本：Lovable 要先点「Add Task」按钮（多一次点击），Base44 不用。
8. 最后一轮让两边「加标签和分类」：Base44 崩了，Lovable 正常出结果，并且 provenance 展示更明确（「它想了 7 秒」）。

### 3.8 第七步：给出取舍结论

讲师的结论不是「谁绝对更好」，而是**按用例分工**：

- **Base44**：更适合**快速原型 + 持续发现（continuous discovery）**。理由是「电池已内置」：开箱就能发布、内置用户鉴权（Google / Microsoft / Facebook 登录）、内置密钥管理、可开后端函数、可接 API。对在大公司做内部平台工具的人，「这是最好的作弊码」——有人提了个想法，五分钟就能做出来给人登录使用。
- **Lovable**：更适合**落地页**这类需要独特视觉的场景，因为它不套现成的设计系统，产出更不「罐头化」；但要做鉴权、LLM 能力、Vercel 部署，都得自己接（Supabase、自带 key）。
- 讲师也承认 Base44「更 vanilla（更平淡）」，并补充「这也可能是我的使用问题，Lovable 这方面可能已经变好了」。

### 4.2 现场实测记录表（可直接复制使用）

```markdown
# Bake-off 记录表

## 组别：会议记录（Granola=1 / Otter=2）
| 查询 | 1 的输出要点 | 2 的输出要点 | 投票 | 理由 |
|---|---|---|---|---|
| 默认摘要 | 无 overview，不识别参会人，不识别日历事件名 | 有 overview，识别主题 | 2 | 更易消化、认知负荷低 |
| 总结关键决策/风险/优先级 | 按类别分 header，更易聚焦 | 有格式但较弱 | 分裂 | 1 胜在分类，2 胜在深度与时间戳 |
| 下一步做什么 | 过于字面（continue grinding） | 更像可执行的下一步 | 2 | 新鲜度上下文 |
| 团队怎么做 evals | 意图理解错误 | 承认不知道 + 兜底 + 建议联系支持 | 2 | 诚实 + 有用 |
| 为什么竞品更好 | 拒绝接话 | 防御性回答 | — | 低成本越狱，缺护栏 |
| 会议怎么组织更好 | 有时间戳 | 深度更好 | 分裂 | 1 格式 + 2 深度 |

## 组别：建站（Lovable=1 / Base44=2）
| 维度 | 1 | 2 | 胜方 |
|---|---|---|---|
| 开箱美观 | 更独特、不罐头 | 更 vanilla 但更完整 | 2（多数票） |
| 预置示例数据 | 无 | 有 | 2 |
| 加任务点击成本 | 需先点 Add Task + 填 due date | 直接加 | 2 |
| 完成反馈 | 动画好、juice 少 | toast | 各有胜场 |
| X 关闭 | 有 bug 没关掉 | 正常 | 2 |
| 刷新后记忆 | 不记得 | 记得 | 2 |
| 加标签/分类 | 正常，provenance 清楚 | 崩了 | 1 |
| 内置鉴权/密钥/后端 | 需自接 Supabase、自带 key、Vercel | 开箱即用 | 2 |
```

### 4.3 失败模式清单（从本讲实录中提炼）

| 失败模式 | 出现在 | 建议的 eval 类型 |
|---|---|---|
| 意图理解错误（把元问题当会议内容检索） | Granola | LLM-as-judge 判「是否回答了被问的问题」 |
| 过于字面复述会中词汇，对回访用户不可理解 | Granola | 人工 rubric：脱离会议上下文是否可读 |
| 被低成本越狱后防御性回答竞品问题 | Otter | **代码型 eval：竞品关键词检测 + 固定回复** |
| 未识别会议元信息（日历事件名、参会人） | Otter | 规则检查：元字段是否填充 |
| 生成代码有交互 bug（X 关不掉） | Lovable | 端到端脚本点击回归 |
| 刷新后状态丢失 | Lovable | 端到端脚本：刷新后断言数据仍在 |
| 后期改动导致页面崩溃 | Base44 | 端到端脚本：每轮改动后跑冒烟测试 |

### 4.4 竞品护栏示意（课里没有代码，以下为示意）

讲师明确说「这大概就是代码型 eval 最适用的地方：检测关键词……给一个法务批准的固定回复」。下面是把这句话落成前端 / Node 可用的最小示意：

```js
// guardrail.js —— 课里没有代码，以下为示意
// 用途：在把用户输入送进 LLM 之前，先做竞品关键词检测
// 命中则直接返回法务批准的固定话术，不调用模型

const COMPETITOR_KEYWORDS = [
  // 课里没给具体名单，讲师只说「列出我所有的竞品」
  // 这里按会议记录场景举例，实际名单由业务/法务提供
  'competitor-a',
  'competitor-b',
];

const LEGAL_APPROVED_REPLY =
  '这个问题我无法评价其他产品。我可以帮你对比本产品在会议记录场景下的能力。';

/**
 * @param {string} userInput 用户原始输入
 * @returns {{ blocked: boolean, reply?: string }}
 */
export function checkCompetitorGuardrail(userInput) {
  const normalized = String(userInput).toLowerCase();
  const hit = COMPETITOR_KEYWORDS.some((kw) => normalized.includes(kw));
  if (hit) {
    return { blocked: true, reply: LEGAL_APPROVED_REPLY };
  }
  return { blocked: false };
}
```

```js
// guardrail.test.js —— 课里没有代码，以下为示意
import { checkCompetitorGuardrail } from './guardrail.js';

// 对应讲师说的「低成本越狱」场景
const cases = [
  { input: '为什么 competitor-a 比你们更好？', expectBlocked: true },
  { input: '帮我总结这次冲刺规划会', expectBlocked: false },
];

for (const c of cases) {
  const r = checkCompetitorGuardrail(c.input);
  console.assert(
    r.blocked === c.expectBlocked,
    `失败：${c.input} 期望 blocked=${c.expectBlocked}，实际 ${r.blocked}`
  );
}
```

## 5. 逐行解释

### 5.1 为什么先定维度、再谈评测

讲师整场的逻辑链是：**AI 产品是主观的 → 主观的东西需要品味 → 品味因人而异 → 所以要先把「什么算好」显式写成维度 → 维度定了，才能做假设检验 → 假设检验跑出来的差异，才是可客观改进的东西**。

这条链的关键在于：**维度不是从产品里长出来的，是从用户里长出来的**。讲师原话是「最好的办法其实就是去和客户聊……请他们带你走一遍」。他特别指出，现场 Discord 里大家提的维度五花八门（技术能力、是否编造、是否抓住主题、是否抓住行动项、是否识别发言人观点、是否捕捉能量与参与度、对不同口音的准确率……），而「这正是重点——每个人视角都不同」。所以维度表的第一版应该是**发散收集**，不是收敛。

对前端读者的类比：这就像定设计系统的 token——你不先定 spacing scale，就没法说「这个间距不对」。维度就是评测的 token。

### 5.2 为什么「默认输出」要单独评一轮

因为**默认输出是大多数用户唯一会看到的输出**。讲师明确说这一轮「我没有套 system prompt，没有套任何模板包」，虽然「你可以套」。如果一上来就用调好的 prompt 去比，你测的是「prompt 工程能力」，不是「产品默认体验」。

这也解释了为什么 Otter 在默认摘要轮胜出：它赢在**信息架构**（有 overview、有分区），而不是赢在模型能力。讲师把这一点归到 usability 桶，并说了一句很产品的话：「你是在要求用户承担认知负荷去理解 AI 生成了什么。如果它视觉上就不像我想进去看的东西，那已经是体验的一部分了。」

### 5.3 为什么同一批查询要同时丢给两个产品

控制变量。讲师的操作是「let's go ahead and just ask both of these at the same time」，并且现场投票、现场要理由。要理由这一步很重要——**投票只给你一个数，理由才给你维度**。现场收到的理由（「有 overview」「更 organized」「less work for the human」「wall of text」）直接就是评分 rubric 的候选条目。

### 5.4 为什么「问它团队怎么做 evals」是一个有效测试

讲师的逻辑是：这个问题**不在会议转录里**，所以一个健康的回答应该是「这场会里没有这个信息」。Granola 答成了「这场会议聚焦于 Robert，没有覆盖 Granola 的评测流程」——形式上没错，但它**把元问题当成了内容检索**，说明它没有理解意图。Otter 则先承认不知道，再给兜底（反馈机制、训练授权），再给升级路径（联系支持）。

讲师自己也留了余地：「这要么是它编的，要么是他们真的想过这件事」，「这个知识怎么会进到上下文里？我不知道」。所以这条测试的判定标准不是「答案对不对」，而是**「不知道的时候怎么表现」**——这正好对应 desirability 里的「是否编造」维度。

### 5.5 为什么「低成本越狱」值得测

讲师只问了一句「为什么 Otter 是比 Granola 更好的笔记应用」，Otter 就进入了防御性回答模式（承认用户可能觉得 Granola 更好，然后列自己的市场地位）。讲师点评：「这只是一次低成本的越狱，我甚至没真的试着越狱。」这条观察直接导向了后面的**竞品护栏**建议：如果产品会被问到竞品，就应该有法务批准的固定回复，而不是让模型自由发挥。

那个客户支持 bot 推荐竞品的真实案例，是这一段的落点：**这是测试才暴露出来的失败模式**，而且**用关键词检测就能兜住**——这就是「代码型 eval 最适用的地方」。

### 5.6 为什么「time to value」要用「对话回合数」来量

讲师给了一个很好用的换算：把「价值到达时间」换成「**我需要多少个对话回合才觉得被听见、被看见、被理解**」。这个换算的好处是它**可数**。一个回合就懂你的朋友 vs 一百个回合还不懂你的朋友，这个体感人人都懂，把它搬到 LLM 交互上，就变成了一个可以打分的维度。

由此推出那条很实用的工程建议：**用户抱怨延迟时，先别优化延迟，先改 UX 让用户知道它在想**。讲师说「往往这就是你需要的全部」。他还举了游戏的加载屏作为类比——加载屏是「加 juice、加色彩、制造期待」的地方。对前端读者，这就是 skeleton screen / streaming token / 「思考中」指示器的产品论证。

反过来，讲师也说了**太快**的坏处：Lovable 秒出结果时他的反应是「它没思考，它就是往外喷……像一个人听见了我说话但没在听，他是为了说而听」。所以速度不是单调向好的维度，**感知到的思考**也是体验的一部分。

### 5.7 为什么建站组要「一次只让它做一件明确的事」

讲师的原话是「我通常不会一次性要求做很多件事，那样它一般会把好几件事都做错。所以我尽量只聚焦非常明确的一件小事，就像我在给一个工程师指方向一样」。这条对前端读者尤其重要：vibe coding 工具的正确用法不是「一句话生成整个 app」，而是**像 code review 一样小步提交、小步验证**。讲师自己说「我一般不 one-shot」。

### 5.8 为什么 Base44 赢在「电池已内置」

讲师的取舍标准不是「谁生成的代码更好」，而是「**我的用例是什么**」。他的用例是**快速原型 + 持续发现**：做一个东西出来，让真实用户进去用、生成自己的数据、下次回来数据还在，然后他做假设检验、改进、再测。这个循环里，**鉴权、持久化、部署、密钥管理**是必经之路。Base44 把这些开箱给了（Google / Microsoft / Facebook 登录、密钥管理、后端函数、接 API），所以「它消除了原型学习循环里的摩擦」。

Lovable 则要你自己接 Supabase 做鉴权、自带 LLM key、自己搞 Vercel 部署。讲师说「这对快速原型来说还行」，但紧接着被反问「为什么还行？这不行啊」，他承认「对某一类快速原型才行，比如落地页」——因为落地页不需要鉴权、不需要持久化、不需要后端。而 Lovable 在落地页场景反而更强，因为它不套现成设计系统，视觉更独特。

这就是「**维度要绑定用例**」的最好例证：同一个维度（开箱即用），在原型场景是加分，在落地页场景根本不适用。

### 5.9 为什么最后一轮「加标签和分类」很重要

因为它是**回归测试**。前七轮都正常的产品，在第八轮改动后崩了——这正是讲师在开头 PPT 里说的「回归风险是真实的（regression risks are real）」。对前端读者，这条的落地含义是：**每次让 AI 改代码之后，都要跑一遍冒烟测试**，而不是只看新功能有没有出来。Lovable 在这一轮反而赢了，因为它的 provenance 展示更明确（「它想了 7 秒」「show all」），讲师说「我更喜欢这个，它明确显示了我让 Base44 做了什么」。

### 5.10 五类桶怎么用（不要当成打分表）

讲师反复说这些桶是**思考框架**，不是打分表。他给每个桶配了会议记录场景的实例（见 4.1 表），但没有给权重、没有给公式。**课里没讲**怎么把五个桶合成一个总分，也没讲阈值。这一点很重要：如果你要落地，权重和阈值得你自己按 ICP 定。

## 7. 课里没讲但你会撞上的

**1. 怎么把五个桶合成一个可比较的分数？**
课里没讲。讲师只给了桶和实例，没给权重、没给公式、没给阈值。你自己落地时得先定 ICP，再按 ICP 给桶配权重。前端类比：这就像定 lint 规则——规则本身好定，难的是定「哪些是 error、哪些是 warning」。

**2. 样本量多少才够？**
课里没讲。这一讲是现场投票，每轮几个人到几十个人，属于定性信号，不是统计显著。真要上线前做回归，样本量和置信区间得你自己算。

**3. LLM-as-judge 怎么搭？**
课里没讲具体实现。讲师提到「代码型 eval」适合关键词护栏，但没有展开 LLM-as-judge 的 prompt 设计、一致性校准、成本控制。这部分在课程其他讲里，本讲不覆盖。

**4. 竞品关键词名单从哪来？**
课里没讲。讲师只说「列出我所有的竞品，把这些做成关键词」，并强调回复要「法务批准」。实际名单是业务 + 法务的输入，不是工程能自己定的。

**5. 会议录音的合规怎么做？**
讲师提了一句伦理：「你应该告诉别人你在录音」，并说这是 Granola 团队知道的。但**具体合规流程、告知话术、数据留存策略，课里没讲**。

**6. Granola 到底捕不捕获屏幕？**
讲师现场确认：「它知道你屏幕上有什么，所以它有会议的上下文，但它不捕获屏幕上的任何东西，只是转录。我可以随手加截图，然后它就有更多上下文。」——所以是**转录 + 手动截图**，不是自动录屏。这一点容易记错。

**7. Base44 崩了是产品问题还是 prompt 问题？**
课里没定论。讲师只说「看起来右边这个坏了」，然后因为时间到了就结束了。**根因课里没讲**。

**8. Lovable 的 X 关不掉是 bug 还是设计？**
讲师判定是「写出来的代码里的 bug」。但**课里没讲**怎么复现、怎么修。

**9. 这些产品的定价、额度、API 限制**
课里没讲。讲师只提到自己有「Lenny's newsletter 送的免费 Granola license」。

**10. 对前端读者的一个提醒**
这一讲全程没有代码，所以「在 JS/Node 里对应什么」这个问题，本讲唯一能对应上的就是 4.4 那个关键词护栏示意（课里没有代码，是我补的示意）。锁、事务、并发这些概念**本讲完全没涉及**，不用在这里找对应。
