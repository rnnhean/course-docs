[06:59] Find slow HTTP requests for resource name and suggest fixes. Section 10.4.3, what are MCP and agentic tool calling? Before we finish, it would be useful to understand how MCP works. Agentic coding assistants rely on the same types of large language models, LLMs, covered in Chapter 5. On its own, however, an LLM wouldn't be able to automate the process of writing code and placing it in the right files. To do that,
[07:29] it needs tools that extend its capabilities. Agentic Tool Calling and MCP are two closely related concepts that shape how modern coding assistants operate. They move AI systems from passive text generators to active participants in a development workflow. Agentic Tool Calling refers to a pattern in which a language model can decide when and how to use external tools to complete a task. Instead of producing only text, the model can invoke structured actions such as reading a file, running a test suite,
[07:58] executing a shell command, querying a database, and calling an API. The model analyzes the user request, determines whether additional information or computation is required, selects the appropriate tool, and then incorporates the result back into its reasoning. This gives the assistant a form of agency. It can plan, act, observe the result, and refine its next step. In the context of coding assistance, agentic tool calling enables much more than code completion.
[08:28] Consider an assistant integrated into an editor. When a developer asks it to refactor a class, the assistant might first read the relevant files from the repository. Then it might search for references across the code base, generate updated implementations, run the test suite, and inspect failures. If tests fail, it can iterate by adjusting the code and rerunning tests until they pass. Each step is a tool invocation. The model orchestrates actions in a loop.
[08:56] rather than responding with a single block of text. Claude Code is an example of a coding assistant that uses this pattern. When asked to implement a feature, it can inspect the project structure, read specific files, and propose changes grounded in the actual code base. It can run commands such as linters or tests, and adapt its output based on the results. This transforms the assistant into a collaborative agent that operates within the developer's environment. Underneath these systems,
[09:26] the model needs a standardized way to discover and use tools. This is where MCP becomes relevant. MCP is a specification that defines how tools, resources, and contextual information are exposed to a language model. Think of it as an API for AI agents. Instead of hard coding tool integrations for each assistant, MCP provides a consistent contract. Tools describe their capabilities, input schema, and output schema in a structured way.
[09:54] Then the model can select and call them through a predictable interface. As with an interaction using a REST API or GRPC, there's the concept of a server and a client. The AI agent acts as the client. The MCP server, as the name suggests, acts as the server. The API is what the agent can access, a facade that delivers data from a variety of sources, such as databases, files, and documents.
[10:20] It's not conceptually different from the REST APIs we've looked at many times throughout this book. Figure 10.4 shows how an agent interacts with the MCP server. [10:48] Each tool advertises what arguments it expects and what kind of result it returns. The model receives this catalog of capabilities as part of its context. When it determines that it needs more information, it issues a tool call that conforms to the protocol. The host system executes the tool and feeds the result back to the model. This loop continues until the task is complete.
