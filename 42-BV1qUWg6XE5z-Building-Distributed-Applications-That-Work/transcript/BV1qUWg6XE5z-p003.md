Section 1.2.1, starting several resources. A single application normally has one obvious starting point. You run the executable, wait for it to become ready and begin using it. By contrast, a distributed application may require several resources to start. The storefront.
[04:40] One or more APIs, background services, databases, caches, message brokers, other supporting infrastructure. Starting these components manually is inconvenient. A developer may have to launch several projects from separate terminal windows, start one or more containers, and confirm that every resource is using the correct configuration. The order can also matter.
[05:07] The storefront may depend on the catalog API, and the API may depend on a database. A background service may require the message broker to be available before it can begin consuming messages. Starting a process doesn't necessarily mean that it's ready to accept requests. A database container may be running while it's still initializing. An API process may have started, but may not yet be able to connect to its dependencies. Without coordination,
[05:33] the storefront could begin sending requests before the catalog API is ready. The API could start before its database is available. The result may be a temporary failure that disappears when the application is restarted, making the problem difficult to reproduce and diagnose. Section 1.2.2 – Managing Addresses and Configuration Separately running components must know how to reach one another. Suppose that the storefront sends HTTP requests to the catalog API.
[06:03] To make the call, it needs an address containing a host name and port, such as HTTPS localhost 7243. That address may be different on another developer's machine. It may also change when a port is already in use. A containerized service may have both an internal container port and a different host port. In a deployed environment, the service may use a domain name system, DNS name, rather than a local host address. The same problem applies to infrastructure resources.
[06:32] An API may require a database connection string, a cache endpoint, message broker credentials, an identity provider address, storage configuration. Hard coding these values makes the application fragile and environment specific. Maintaining separate configuration files can help, but developers must still make sure that the values match the resources currently running on their machines. The more components the system contains,
[07:02] the more configuration must remain synchronized. Section 1.2.3, dealing with network boundaries. Inside a single process, one module can usually call another directly. In a distributed application, communication crosses a network boundary. A network request can fail for reasons that don't exist in a local method call, following are a few of those reasons. The destination service may not be running.
[07:29] The service may still be starting. The configured address may be incorrect. The request may time out. The connection may be interrupted. The destination may respond slowly or return an error. Even when every service runs on the same development machine, communication still uses network protocols such as HTTP or WebSocket. Therefore, the application must handle the possibility that a dependency is temporarily unavailable.
[07:59] This also means that a failure in one component can affect several others. If the catalog API is unavailable, the storefront may start successfully, but the product catalog might not work. If the message broker is unavailable, customers may be able to browse products while order processing fails. As a result, a distributed application can be partially operational. Understanding which parts are running, which parts are healthy, and which dependencies are failing is an important part of development.
